What Changed in Copilot Studio Billing

The GitHub Copilot harness became generally available on August 3, 2026 and brought a second billing model with it. What changed, what did not, and the decisions that now sit in front of every agent you build. · August 2026

The one thing to remember: Copilot Studio now has two billing models, and the harness you choose decides which one applies. Agents on the GitHub Copilot harness bill on usage, start consuming credits the moment you begin building rather than when you publish, and carry no Microsoft 365 Copilot license inclusion. Everything you already know about Copilot Studio billing still holds — but only for the standard and Copilot chat harnesses.

What actually changed

Until August 2026, Copilot Studio billing was a single story. Agents consumed Copilot Credits against a published per-event rate card, employee-facing usage by a Microsoft 365 Copilot licensed user was included at no charge, and metering began when you published.

That story is intact. What changed is that it is no longer the only story. Copilot Studio is now a multi-harness platform. A harness is the runtime sitting between what you author and the model that reasons — it decides when to call the model, what context to send it, how to interpret the response, and which tools to invoke. There are three, you pick one when the agent is created, and that choice sets the billing model for the life of the agent.

The name is the most common misread. The GitHub Copilot harness does not require GitHub Copilot. There are no GitHub Copilot licenses to buy and no GitHub configuration involved. The name refers to the orchestration lineage the runtime came from, not a dependency or a prerequisite. If someone in the room hears "GitHub" and assumes a separate purchase, correct it early.

Three harnesses, two billing models

HarnessBuilt forHow it bills
Standard Rule-based agents and structured, predictable conversations. You define the topics, prompts, and paths. Copilot Credits on the published per-event rate card. Microsoft 365 Copilot license inclusion applies.
Copilot chat Extending Microsoft 365 Copilot Chat with your organization's knowledge. Publishes to internal teams. Consumption-based, or included in the Microsoft 365 Copilot user subscription license.
GitHub Copilot Reasoning-heavy, multistep business processes. Takes a goal, breaks it into steps, calls tools, and recovers when a step fails. Usage-based Copilot Credits. Always billed. No license inclusion.

The practical consequence is that "how much does a Copilot Studio agent cost" is no longer answerable without first asking which harness it runs on. Agents are labeled in the Copilot Studio agent inventory, so this is a question anyone can answer for their own estate in a couple of minutes.

There is no migration between harnesses. An agent created on one harness cannot be transferred to another. Capabilities are optimized per harness and are not portable, so moving an agent means rebuilding it. Treat harness selection as a near-irreversible design decision rather than a setting you can revisit later.

Four assumptions that break

If your understanding of Copilot Studio billing was formed before August 2026, four things you reasonably believe are no longer universally true. Each one holds on the standard harness and fails on the GitHub Copilot harness.

1

Billing no longer starts at publish

This is the reversal that catches teams out, and it is the single most important line on this page. On the standard harness, cost begins when the agent goes live. On the GitHub Copilot harness, credits are consumed from the moment you start building. Microsoft names three build-time activities explicitly: creating a solution with natural language, previewing and testing the agent, and generating and creating agent evaluations.

The implication for planning is direct. A team iterating heavily or running large evaluation suites is generating real consumption on an agent that may never ship. Build-phase spend has to be forecast as its own budget line, separate from runtime.

2

The Microsoft 365 Copilot license inclusion does not carry over

On the standard harness, employee-facing usage by a Microsoft 365 Copilot licensed user, running under that user's authenticated identity and within fair-use limits, is included at no charge. That rule is the commercial premise behind a great many Copilot Studio business cases.

It does not apply to the GitHub Copilot harness. Usage is billed regardless of what the end user is licensed for. If an existing business case rests on license inclusion, moving that scenario to the GitHub Copilot harness invalidates the economics behind it.

3

There is no per-event rate card to optimize against

The familiar table of fixed prices per event does not describe this harness. Consumption is usage-based and measured against the work performed. Microsoft states that credits are charged for large language model tokens, for tools (including knowledge sources and MCP servers), and for the harness itself.

So the optimization technique of counting events and multiplying by a published rate does not transfer. You are modeling work performed, not events fired.

4

Running out of credits stops your builders, not just your users

Enforcement on the standard harness disables agents. On the GitHub Copilot harness it reaches further back into the lifecycle. When an environment has no credits available, end users stop getting responses and makers lose the ability to author with natural language, to preview and test, and to generate or create evaluations.

On a shared build environment this matters a great deal: one team exhausting the pool halts everyone's authoring, not only production traffic.

What a task costs

Because there is no per-event rate card, Microsoft publishes planning bands instead. Runtime cost is driven by four inputs — the models selected for the task, the runtime orchestration coordinating the work across steps, the context retrieved to ground it, and the tools invoked to act on it. Those same four inputs are the right diagnostic frame when someone asks why a particular task cost what it did.

The capability difference is real and so is the cost difference. What did not change

It is worth being precise about the blast radius here, because the change is narrower than the noise around it suggests.

Unchanged

  • Standard and Copilot chat harness billing is exactly as it was.
  • Existing agents keep running. Nothing is switched off.
  • New agents can still be created on the standard harness.
  • Microsoft 365 Copilot license inclusion continues for eligible employee-facing standard harness scenarios.
  • Copilot Credits remain the common currency across the platform.
  • Purchasing vehicles are unchanged: prepaid packs, pay-as-you-go, and prepurchase plans.

New, and opt-in

  • A third harness exists, selected per agent at creation.
  • That harness bills on usage with no license inclusion.
  • Build-time activity meters on that harness.
  • Enforcement on that harness also blocks authoring.

There is no requirement to move anything. The standard harness remains available precisely so teams can keep the economics they already have. Frame this as a capability and cost trade you opt into, never as a migration mandate.

What happens when credits run out

The two models also diverge on what enforcement looks like in practice.

Standard harnessGitHub Copilot harness
Trigger Tenant reaches 125% of prepaid capacity. Environment has no credits allocated or has consumed its allocation.
Effect on end users Custom agents are disabled. In-flight conversations finish; subsequent attempts are rejected. Agents stop responding to requests.
Effect on makers None. Authoring continues. Authoring stops too — no natural language authoring, no preview or test, no generating evaluations.
Grace Microsoft permits a degree of overage as a buffer rather than cutting off instantly, so business processes are not blocked the moment a threshold is crossed.
Recovery Three options in both cases: reallocate capacity from elsewhere in the tenant, purchase more capacity, or attach a consumptive or pay-as-you-go meter.

Worth noting separately: agent flow enforcement behaves differently again. When prepaid capacity is fully consumed, new agent flow runs are blocked rather than the parent agent being disabled. Runs already in progress complete, the agent continues to serve non-flow interactions, and enforcement resets monthly when credits renew. Power Automate cloud flows are not affected at all — they bill on Power Automate licensing and sit outside Copilot Studio enforcement entirely.

How to decide, and what to do now

The working rule for harness selection

1

Customizing Microsoft 365 Copilot itself, so employees get grounded answers without leaving their everyday tools? Copilot chat harness.

2

Deterministic, rules-driven, topic-based work where you want predictable answers? Standard harness. This is also the right answer whenever Microsoft 365 Copilot license inclusion is the commercial premise of the project.

3

Genuinely agentic work — many steps, many sources, ambiguous decisions, documents to create and reason over, recovery when a step fails? GitHub Copilot harness, and only once usage-based billing has been understood and accepted.

Capability alone should never select the harness. The billing model is a co-equal gate. The most expensive mistake available here is choosing the GitHub Copilot harness for its capabilities, discovering the cost profile afterwards, and finding there is no migration path back.

A short checklist

  • Inventory what you have. Agents are labeled by harness in the Copilot Studio agent inventory. Know the split before you plan anything.
  • Separate build spend from runtime spend in any forecast that includes the GitHub Copilot harness. They are genuinely different line items now.
  • Allocate credits per environment rather than letting everything draw on an undifferentiated tenant pool. Environment design is the practical governance boundary.
  • Set per-agent monthly limits in the Power Platform admin center under Licensing, Copilot Studio, Manage Agents, so a single agent cannot drain the pool before anyone notices.
  • Watch shared build environments especially. Exhausting credits there stops authoring for every team using it.
  • Check consumption where it is actually reported. Per-agent figures sit on the agent's Monitor page; environment and tenant rollups sit under Licensing, Copilot Studio in the Power Platform admin center.
  • Re-verify the numbers before you commit to them. Rates, bands, thresholds, and inclusions in this space change frequently.
