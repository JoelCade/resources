Copilot Studio and Microsoft Foundry: How the Two Halves Fit Together

The five supported seams between the low-code agent platform and the pro-code AI platform, what each one is actually for, and how to choose between them without rebuilding your agent. · August 2026

The one thing to remember: Copilot Studio and Microsoft Foundry are not two competing ways to build the same agent. Copilot Studio is the experience, orchestration and governance layer where an agent meets its users. Foundry is the model, retrieval, and evaluation layer underneath it. The strongest architectures use both, and there are five documented seams for wiring them together. Picking the right seam is the whole design decision.

A note on naming

Microsoft documentation is mid-rename. Newer articles say Microsoft Foundry; older articles, product surfaces, and most existing customer material say Azure AI Foundry. They are the same platform. In this page, "Foundry" means both. Where a feature name still carries the old branding in the product UI — for example the Azure AI Foundry models for prompts feature inside Copilot Studio — the original name is kept so it is findable.

Note also that some of the connection surfaces described here are in preview. Preview features change. Confirm current state in the linked documentation before committing an architecture to a customer.

Two layers, not two products

The most common architectural mistake is to treat the choice as "Copilot Studio or Foundry" and then argue about which one is more capable. That framing produces bad designs in both directions: over-engineered Foundry builds that reinvent channel plumbing and authentication that Copilot Studio already ships, and over-stretched Copilot Studio builds that hit a genuine model, retrieval, or evaluation ceiling and have nowhere to go.

A cleaner frame is to ask which layer a given requirement belongs to.

Concern Copilot Studio is the natural home Foundry is the natural home
Where users meet the agent Microsoft 365 Copilot, Teams, web chat, voice, custom channels, Power Platform surfaces Not its job. Foundry exposes endpoints, not end-user channels.
Identity and permissions User authentication, connectors that respect the signed-in user, Dataverse security Service-level identity, managed identity, key and certificate custody
Model selection Platform-managed default models, good enough for most agents Explicit choice from a large model catalog, versioning, capacity, fine-tuning
Retrieval and grounding Built-in knowledge sources over SharePoint, Dataverse, files, public sites Purpose-built indexes, hybrid and agentic retrieval, tuned relevance
Business logic Topics, agent flows, connectors, human-in-the-loop approval steps Custom code, arbitrary SDK logic, non-Microsoft frameworks
Evaluation and tracing In-product testing, analytics, activity trace for a single conversation Systematic evaluation runs, trace ingestion, telemetry across many agents
Lifecycle and shipping Solutions, environments, pipelines, maker-accessible change control Code repositories, deployment pipelines, engineering-owned release process
Metering Copilot Credits, with a billing policy on the environment Azure consumption against a subscription

Read that table as a routing rule rather than a scorecard. A requirement that sits firmly in the right-hand column does not mean the agent belongs in Foundry. It means that one capability should come from Foundry and be attached to a Copilot Studio agent through one of the seams below.

The five seams

These are the documented, supported integration points as of August 2026. They are listed roughly in order of how invasive they are, from "change a dropdown" to "instrument your whole estate."

1

Foundry models inside Copilot Studio prompts

Also called bring your own model. The Azure AI Foundry models for prompts feature lets a prompt inside Copilot Studio — and also inside Power Apps and Power Automate — run against a model you choose from the Foundry model catalog rather than the platform default. Microsoft cites frontier OpenAI models, Llama, DeepSeek, and more than 1,800 models in the catalog.

Use it when the default model is the specific thing failing you: you need a reasoning model for a hard extraction task, a small cheap model for a high-volume classification step, an open-weight model for a licensing or sovereignty reason, or a domain-specific model that simply knows the vocabulary better.

Do not use it as a first move when an agent gives poor answers. Most poor answers are a retrieval or instruction problem, not a model problem, and swapping the model hides the real defect.

Lowest effortNo Azure plumbing for the makerPrompt-scoped
2

Foundry IQ knowledge bases as a tool

A Foundry IQ knowledge base bundles one or more enterprise data sources with retrieval and relevance settings into a single reusable asset built in Foundry. Copilot Studio connects to it as a tool on the agent's Build tab, authenticating with an API key, a client certificate, a service principal, or integrated Microsoft Entra ID. Retrieval then happens in Foundry and the returned items are handed back for the agent to compose its answer — visible as a distinct retrieval step in the activity trace.

Use it when grounding quality is the ceiling: built-in knowledge sources answer inconsistently, the corpus needs chunking or relevance tuning you cannot express in Copilot Studio, or several agents must share one governed, centrally maintained retrieval asset instead of each configuring their own sources.

Practical constraints: an agent can hold only one Foundry IQ connection, and tuning belongs in the knowledge base itself, not in Copilot Studio. If results are wrong, fix the knowledge base with its owner rather than adding instructions to compensate.

Shared retrieval assetOne connection per agentTune in Foundry
3

A Foundry agent as a connected agent Preview

An agent built in Foundry Agent Service can be attached to a Copilot Studio agent as a connected agent. From the Agents page you choose Add an agent, then Connect to an external agent, then Microsoft Foundry. The connection needs the Foundry project endpoint URL, and the connected agent needs the agent ID plus a name and description. The parent agent uses that description to decide when to delegate, so the description is functional configuration, not documentation.

Use it when real engineering work already exists in Foundry — custom code, a specialist reasoning loop, an SDK-based pipeline — and the requirement is to make it reachable from Microsoft 365 and Teams without porting it. Copilot Studio supplies the channel, the identity, and the orchestration; Foundry keeps the logic.

Known constraint: the target agent must have been created in the current Foundry portal. Connecting to an agent created in the previous portal fails with a 404 — Version not found error, which is a portal-generation problem rather than a permissions problem and is easy to misdiagnose.

DelegationDescription drives routingNew portal only
4

Agents over the A2A protocol

Copilot Studio can also connect to any agent that speaks the open Agent2Agent (A2A) protocol, regardless of framework or host. You add an agent, choose A2A, and supply a publicly reachable endpoint URL plus the authentication the endpoint requires.

Use it when the specialist agent is not in Foundry at all — a partner-built agent, a service in another cloud, a team's own framework — and you want one interoperable contract rather than a bespoke connector.

Watch the exposure. Microsoft's own guidance is explicit that development tunnels are for local demonstration only. Production A2A endpoints belong behind a properly authenticated web app or containerized service. An unauthenticated tunnel that works beautifully in a demo is a genuine security finding if it survives into production.

Open standardFramework-agnosticAuthenticate in production
5

Registering agents in Foundry for observability and evaluation Preview

The traffic can also flow the other way. Foundry supports registering external agents so their traces ingest into Application Insights and surface in the Foundry portal alongside natively hosted agents, typically within a few minutes. That gives you evaluation runs and tracing across agents that were not built in Foundry.

Use it when the estate has grown past what per-agent analytics can answer: you need one place to compare quality across agents, to trace a multi-agent request end to end, or to run repeatable evaluations as part of a release gate rather than eyeballing test conversations.

This is the seam most often skipped and most often regretted. It is also the one that turns a collection of individual agents into something an operations team can actually run.

The shared tool plane underneath all five

Both platforms treat Model Context Protocol (MCP) servers as tools. An MCP server added to a Copilot Studio agent exposes its tools on the agent's Tools tab, and Foundry agents consume MCP servers as well. That matters architecturally: a capability published once as an MCP server is reachable from either platform, so the tool layer does not have to be rebuilt when an agent moves or when a second agent needs the same capability. Where a capability is genuinely shared, publishing it as an MCP server is usually a better investment than wiring it separately into each agent.

Choosing a seam

Most design conversations resolve quickly once the symptom is named precisely.

The symptom The seam Why
Answers are fluent but factually wrong or inconsistent Foundry IQ knowledge base (seam 2) This is almost always retrieval, not reasoning. Fix grounding before touching the model.
The task itself is genuinely hard reasoning, extraction, or classification Foundry models in prompts (seam 1) Model capability is the real constraint, and it is prompt-scoped so the blast radius is small.
Working code already exists and a rewrite is not on the table Connected Foundry agent (seam 3) Wrap and reach it rather than porting logic into a low-code surface.
The specialist agent is outside Foundry entirely A2A (seam 4) One open contract beats a bespoke integration per partner or per cloud.
Nobody can say whether the agents are getting better or worse Register for observability (seam 5) Quality you cannot measure across the estate is quality you cannot manage.
Two agents need the same capability Publish it as an MCP server Build the tool once and let both platforms consume it.
The requirement is a scheduled, non-conversational generation step Neither seam — reconsider the shape A Copilot Studio workflow may remove the Foundry infrastructure entirely. See the note below.
A genuine either/or case. Not every requirement needs both platforms. When an application needs a non-conversational, on-demand generation step — a button or a schedule that produces structured output, with no user turn — a Copilot Studio workflow with an inline agent step can do the whole job, removing the Foundry resource, capacity, and key-custody plumbing. That is a real simplification, and for many organizations the procurement path is easier. It is not free, though. It converts an Azure bill into Copilot Credit consumption and still requires a billing policy on the environment, so present it as a change of meter rather than a removal of cost.

A worked shape

A pattern that recurs across enterprise builds, using four of the five seams:

Front of house

Copilot Studio

  • The agent users actually talk to, published to Microsoft 365 Copilot and Teams
  • User authentication, so every downstream call runs as the signed-in person
  • Topics and agent flows for the deterministic paths that must never improvise
  • Human-in-the-loop approval before anything is written back to a system of record
  • Solutions and pipelines carrying the change from development to production
Back of house

Foundry

  • A knowledge base over the governed document corpus, attached as a tool
  • A chosen model on the one prompt where the default was not good enough
  • A connected agent wrapping the existing engineering-owned pipeline
  • Trace ingestion and evaluation runs feeding the release gate
  • Shared capabilities published as MCP servers for reuse

What makes this shape durable is that the seams are narrow. The channel, the identity model, and the approval flow are unchanged if the model choice changes. The knowledge base can be retuned without redeploying the agent. The connected agent can be rewritten in Foundry without the Copilot Studio side knowing. Each seam is a contract, and each contract can be renegotiated on its own.

Five mistakes worth avoiding

Treating the choice as a platform bake-off

"Copilot Studio versus Foundry" is rarely the real question. The real question is which layer a specific requirement belongs to. Teams that argue platforms tend to rebuild channels and authentication they already had, or stretch a low-code surface past its evaluation and model-control ceiling.

Reaching for a bigger model to fix a grounding problem

Swapping the model when retrieval is the defect produces a more expensive agent that is confidently wrong in more fluent prose. Diagnose grounding first: check what the agent actually retrieved before you change what it reasons with.

Writing thin connected-agent descriptions

The description on a connected agent is what the parent agent uses to decide when to delegate. A vague description that overlaps with other tools produces routing that looks random. Treat description text as configuration and make it specific enough to be mutually exclusive from its neighbors.

Letting demo-grade exposure reach production

Development tunnels and unauthenticated endpoints are appropriate for a local demonstration and nowhere else. The gap between the demo topology and a supportable one is real work; budget it rather than discovering it at go-live.

Deferring observability until there is a problem

Tracing and evaluation are cheapest to add while the estate is small and most valuable once it is not. Standing them up after an incident means reconstructing history that was never captured.
