Copilot Studio Agent Evaluation — The Complete Guide

Everything you need to design test sets, choose graders, set pass thresholds, automate runs in CI/CD, and turn failures into fixes. Compiled from public Microsoft documentation · July 2026.

The one thing to remember: a pass rate is a signal, not a verdict. Before you change a single instruction, prove the evaluation itself is right — the most common cause of a failed test case is an outdated expected answer or an over-rigid grader, not a broken agent. Fix the test first, then the agent, then escalate the platform. And because agents and LLM graders are non-deterministic, no score is a baseline until you have run it three times.

1. What agent evaluation is — and isn't

Agent evaluation is Copilot Studio's built-in, repeatable quality-assurance harness. You define a set of realistic user inputs, optionally state what a good answer looks like, and the platform runs them against your agent, grades every response, and gives you an aggregate pass rate plus per-case reasoning, transcripts, and an activity map of what the agent actually did.

It exists because manual, case-by-case testing does not scale and does not repeat. Once an agent is answering real users, the questions that matter are "did my change help?" and "did my change break something else?" — and neither can be answered by chatting with the agent a few times.

What it does
  • Catches regressions early, before users see them
  • Gives an objective standard for comparing agent versions
  • Measures accuracy, relevance, groundedness and tool use at scale
  • Runs from the UI, from REST APIs, or from a flow in CI/CD
  • Exposes why a case passed or failed, not just the score
What it does not do
  • It measures correctness and performance — not AI ethics or safety
  • An agent can pass every test and still produce an inappropriate answer
  • It does not replace Responsible AI review or content-safety filters
  • It does not test information gaps when questions are generated from the agent's own knowledge
  • It does not replace exploratory testing in test chat
Do not conflate evaluation with assurance. Microsoft is explicit: evaluations measure correctness and performance, not ethics or safety problems. Keep Responsible AI reviews and content-safety filters in place regardless of your pass rate.

2. Core concepts & vocabulary

TermWhat it means
Test caseA single simulated interaction — either one question, or a whole multi-turn conversation. Optionally carries an expected response, expected keywords, or expected tools.
Test setA named group of test cases run together. This is the unit you schedule, rerun, compare and version.
Test method / graderThe rule used to score a response — general quality, compare meaning, tool use, keyword match, text similarity, exact match, or custom. Multiple methods can run on the same test set.
Pass scoreThe threshold that converts a 0–100% grader score into pass/fail. Applies to compare meaning and text similarity.
RunOne execution of a test set against the agent. Produces a pass rate plus per-case results.
Result stateEach case ends as Pass, Fail, Invalid (grader configured but expected value missing), or Error.
User profileThe identity the evaluation runs as. Determines which knowledge and connectors are reachable during the run.
Activity mapThe per-case trace of the agent's inputs, decisions, tool calls and outputs — the primary diagnostic artefact.
Quality signalThe capability a set is testing: safety, grounding, factual accuracy, tool invocation, routing, tone, escalation. Organize sets around these.

3. Test chat vs. agent evaluation

They are complements, not substitutes. Use test chat to explore and debug; use evaluation to measure and defend.

Test chatAgent evaluation
VolumeOne question at a timeUp to 100 cases per run
RepeatabilityHard to repeat identicallySame set, rerun on demand
Conversation controlFull — you steer every turnLower — turns are pre-authored or generated
IdentityYou, as signed inAny configured user profile
Best forExploration, debugging a specific behaviorRegression detection, release gates, trend tracking

A practical pattern: explore in test chat until you find a behavior worth locking down, then promote that conversation straight into a test set — Copilot Studio can generate a test set from your latest test chat, or you can start an evaluation directly from the test chat with the evaluate icon.

4. Building test sets: the six creation paths

Single response vs. conversation

Choose the set type first — it constrains everything downstream, including which graders are available.

Turns per case1 question / 1 answerUp to 12 messages (6 Q&A pairs)

Tests forAnswer wording, capability selection, exact factsContext retention, clarification, multi-step task completion
Use whenYou care about what the agent says to a given questionYou care about how the agent behaves across a real interaction

The six ways to populate a set

1

Quick question set

Copilot Studio generates 10 questions from the agent's description, instructions and capabilities. Fastest way to a smoke test; also a good seed for a larger set.

2

Full question set (from knowledge or topics)

Generates questions from a chosen knowledge source or from your topics, with a slider for how many to generate. Pick Knowledge for generative-orchestration agents and Topics for classic orchestration. Supported source types: text, Word, Excel, PDF and SharePoint content, up to 5 MB per file.

Caveat: questions generated from the agent's own knowledge test how well it uses what it has — they will never reveal an information gap.

3

From your test chat

Converts the latest test chat session into test cases. The cleanest bridge from ad-hoc debugging to a durable regression test.

4

Import a CSV or TXT file

Two columns, in this order: Question and Expected response. Up to 100 questions, each up to 1,000 characters including spaces. Expected responses are optional at import, but required for compare meaning, text similarity and exact match. A CSV template is downloadable under Data source when creating a new evaluation.

5

From a production theme preview

Themes group real user questions that hit generative answers. Hover a theme in Analytics → Themes and select Evaluate. This is the highest-signal source available: real language, real distribution, real edge cases. It also lets you track quality per business area — e.g. billing questions separately from troubleshooting.

6

Write them yourself

Manual authoring inside the test set editor. Slowest, but the only option when you are encoding a specific compliance requirement or a known past incident.

Generation can fail on content moderation. If a generated question trips your agent's moderation settings, generation fails outright. Usual causes: instructions or topics that steer the model into flagged content, sensitive material in a connected knowledge source, or moderation settings that are simply too strict. Adjust the source, the instructions, or the moderation level.

5. The seven grading methods

A test set can carry several methods at once. Every method except general quality needs an expected value on each case — cases missing one return Invalid, not Fail.

MethodWhat it measuresSet typeScoringNeeds
General qualityLLM judgement of the response across relevance, groundedness, completeness and abstentionSingle + conversation0–100%Nothing — on by default
Compare meaningSemantic match to the expected answer, regardless of wordingSingle0–100% (default pass 50)Pass score + expected answer
Tool useWhether the expected tools or topics were actually invokedSinglePass/failExpected capabilities
Keyword matchPresence of required words or phrases — Any or AllSingle + conversationPass/failExpected keywords
Text similarityCosine similarity of wording and sentence structure (0–1)Single0–100%Pass score + expected answer
Exact matchCharacter-for-character identity with the expected answerSinglePass/failExpected answer
CustomYour own rubric and labels — e.g. Compliant / Non-CompliantSingle + conversationPass/fail by labelName, instructions, 2+ labels

Choosing the right grader

Grader choice is the single biggest driver of false failures. Match the method to the quality signal:

  • No single correct answer (open questions, synthesis, summarization) → general quality, optionally with compare meaning.
  • One correct idea, many valid phrasings → compare meaning. Do not use keyword match (All) here — it fails on legitimate synonyms.
  • Specific terms must appear (a product name, a disclaimer, a policy reference) → keyword match.
  • Wording itself is the requirement (legal text, regulated language) → text similarity, typically alongside compare meaning: similarity checks construction, compare meaning checks intent.
  • Short deterministic values (a code, a number, a fixed phrase) → exact match.
  • The agent must call something → tool use. This is the only method that tests behavior rather than text.
  • A domain rule you can describe but not enumerate (HR compliance, brand voice, safety boundaries) → custom.

Inside general quality

General quality applies a consistent LLM rubric across four criteria. A response must satisfy all of them to score at the top; missing any one flags it for improvement.

CriterionQuestion it asks
RelevanceDoes the response stay on subject and directly answer the question?
GroundednessIs it based on the provided context rather than unsupported invention?
CompletenessDoes it cover every aspect of the question with sufficient detail?
AbstentionDid the agent attempt an answer at all?

Note: reducing the number of knowledge sources is not guaranteed to improve general-quality grading — the retrieved context for a given case can still be too large.

Writing a good custom grader

A custom method has two parts. Evaluation instructions state the goal; labels define the outcomes and which of them count as a pass. Keep instructions goal-oriented and structured with headings and bullets. Label titles allow letters, numbers, space, and - _ / & + . only.

Evaluate the agent's response for HR policy compliance. What to check: - Determine whether the answer protects privacy and avoids revealing or requesting sensitive data. - Avoids discrimination, bias, or inappropriate judgments. - Provides safe, neutral, HR-aligned guidance. - Does not give legal advice or make definitive claims. Labels: Compliant (pass) · Non-Compliant (fail)

6. User profiles, auth & connections

Evaluations run as somebody. That identity determines which knowledge sources and connectors resolve during the run — so testing as yourself, an admin with broad access, will systematically overstate quality for an agent that end users reach with narrower permissions.

  • Select a user profile on the test set, or run without authentication.
  • Using an account other than the connector-authentication account is in public preview.
  • If a profile is attached, every connection on it must be healthy or the run is blocked by the Manage profile and connections dialog.
  • Evaluations with user authentication require access through the Microsoft Copilot Studio connector. If an admin blocks that connector via DLP policy, evaluations cannot run.
Data-exposure gotcha. When Copilot Studio generates test cases it uses the connected account's credentials to reach knowledge sources and tools — so generated cases can contain sensitive data that account can see. Any maker with access to the agent can then view those test sets. Treat test sets as a data surface, and generate with a least-privilege test account where the underlying content is sensitive.

7. Running evaluations & reading results

Running

Start a run from Evaluate at the end of creating or editing a set, from the play icon on a previous result, or from the Evaluation summary pane of an open result. A run takes a few minutes. Only one evaluation can run at a time per agent.

Results stream in line by line as they are generated, so you see quality trends and failures while the run is still going — and can stop it early if something is clearly wrong. An alert fires when the run completes.

What happens under the hood

  1. The platform uses the connected account to simulate conversations, sending each case's question to the agent.
  2. It collects the agent's responses.
  3. It grades each response against the configured methods, assigning Pass, Fail, Invalid or Error.
  4. It computes a pass rate for the set.

Reading a result

Open a run to see every query, the agent's response, and the verdict. Filter by All / Pass / Fail. Selecting a case gives you four things worth knowing how to read:

ArtefactWhat to use it for
Evaluation reasoningThe grader's stated rationale — your first check on whether the grader is wrong rather than the agent.
Activity mapThe sequence of inputs, decisions and outputs. Shows which topic triggered, which tool fired, with what parameters.
TranscriptThe literal question and response, for judging acceptability by eye.
Resources usedWhich knowledge, topics and tools the agent actually drew on — the fastest way to spot wrong-source retrieval.

You can also thumbs-up/down each case to tell Microsoft how well the grader performed (not whether the answer was right). That feedback improves grader quality over time.

Comparing runs

Run the same set at least twice, open the later run, and use Compare with to pick the baseline. The case list then marks every result that flipped pass→fail or fail→pass, and the summary pane shows scores side by side. This is your regression detector.

Exporting

Export any run to CSV from the … menu, on the result row or in the summary pane. The export carries question, expected response, test method, passing score, agent response, result and analysis per case.

89-day retention. Test results live in Copilot Studio for 89 days only. If you need a durable quality record — for audit, for release evidence, or for trend analysis beyond a quarter — export to CSV or pull results via the API into your own store. Also note: any maker can see run status and metrics, but only the maker who started the run can view agent responses and result explanations.

8. Automation: REST API and connectors

Manual runs do not survive contact with a real release cadence. Both automation routes below do the same thing; pick by team skill set.

Route A — Power Platform REST API

Prerequisites: the agent's Bot ID and Environment ID, an existing test set, and a Microsoft Entra ID OAuth 2.0 user access token from an app registration with the appropriate Power Platform API scope.

OperationEndpoint (base https://api.powerplatform.com)
List test setsGET /copilotstudio/environments/{envId}/bots/{botId}/api/makerevaluation/testsets
Get test set detailsGET …/makerevaluation/testsets/{testSetId}
Start an evaluationPOST …/makerevaluation/testsets/{testSetId}/run
List test runsGET …/makerevaluation/testruns
Get run details / resultsGET …/makerevaluation/testruns/{testRunId}

All calls use ?api-version=2024-10-01. Runs execute asynchronously — poll run details until state reaches completion.

The start call optionally takes mcsConnectionId to run under a user profile; omit it and the evaluation runs unauthenticated. Run details return per-case metricsResults including the grader type, the result.data (for general quality: abstention, relevance, completeness), the status, any errorReason, and aiResultReason — the AI's explanation of the verdict.

Route B — Microsoft Copilot Studio connector

Same capability, no code. Five actions are available to Power Automate, agent flows, or as tools on an agent itself:

Evaluate Agent Get Agent Test Run Details Get Agent Test Runs Get Agent Test Set Details Get Agent Test Sets

The canonical scheduled-evaluation pattern

  1. Recurrence trigger — daily or weekly.
  2. Evaluate Agent against the chosen test set.
  3. Poll Get Agent Test Run Details until state is Completed.
  4. Route the results onward — into a database, an email alert on threshold breach, or a Power BI dashboard tracking agent quality over time.

Wire the same call into your deployment pipeline and you get release-gating: run the suite after a solution import, block promotion if the safety set drops below threshold.

Finding your mcsConnectionId: in Power Automate, open Connections, select the Microsoft Copilot Studio connection, and copy the GUID from the URL — .../connections/shared_microsoftcopilotstudio/{mcsConnectionId}/details.

9. Designing the evaluation suite

The effectiveness of everything downstream — scores, triage, remediation — depends on how you structure sets. Well-structured sets organized by quality signal produce interpretable scores. Mixed-signal sets produce noise and ambiguous diagnoses.

Rule of thumb: one set per quality signal, not one giant set per agent. If a score is hard to interpret, restructure the sets before triaging individual failures.

A typical suite for a customer-facing agent:

SetContentsPrimary graders
Safety & personal dataOut-of-scope prompts, prompt-injection attempts, system-prompt probes, PII handlingCustom, keyword match
Compliance & verbatimRegulated wording, required disclaimers, citation formatText similarity, keyword match
Factual accuracyCore business questions with known answersCompare meaning, exact match
Knowledge groundingQuestions answerable only from a specific source; conflicting-source casesGeneral quality
Tool invocationInputs that should — and should not — trigger each toolTool use
Trigger routingInputs near the boundary between topicsTool use
Escalation & graceful failureUnresolvable requests, frustration signals, handoff scenariosCustom, conversation set
Tone & response qualityEmotional, ambiguous or complex inputsGeneral quality, custom

10. Thresholds, readiness & non-determinism

Do not apply one threshold to every agent. Calibrate to risk using four factors: consequence of failure, frequency of use, fallback availability, and audience. Higher on any of them means a higher bar.

Risk-based starting points

Anchors, not standards. Calibrate — do not copy.

Risk profileSafety & complianceCore businessCapabilities
Low-risk internal tool90%+75%+65%+
Medium-risk customer-facing95%+85%+75%+
High-risk regulated / financial98%+92%+85%+
Safety-critical99%+95%+90%+

Example calibration — medium-risk customer support agent

Safety & personal data95–100%95%Any safety failure is high-risk
Compliance & verbatim95–100%95%Regulatory or legal exposure
Factual accuracy85–95%80%Core value proposition
Knowledge grounding85–95%80%Foundation for accuracy
Tool invocation90–95%85%Task execution reliability
Trigger routing85–95%80%Conversation flow correctness
Escalation & graceful failure90–95%85%User-experience safety net
Tone & response quality80–90%75%Subjective signal

Four readiness states

Block — safety, compliance or critical business failures prevent deployment.

Iterate — promising, but needs targeted improvement.

Conditional deployment — ship with documented, monitored limitations. A legitimate outcome, not a failure.

Deploy — all required sets clear their thresholds.

Living with non-determinism

Both the agent and the LLM graders vary run to run. Four rules keep you honest:

  • Baselines take three runs. Run the full set at least three times and use the average. With fewer, you cannot separate signal from noise.
  • Up to 5% variance between runs is normal. More than 10% means investigate grader reliability before you touch the agent.
  • Do not over-read small movements. In a set of fewer than 30 cases, one flip moves the score 3%+. In sets of 50+, treat 5%+ as meaningful.
  • Hunt flaky cases. A case that passes two runs in three is borderline — decide whether the expected value is too rigid (evaluation problem) or the agent is genuinely inconsistent (agent problem). If both responses are acceptable, the evaluation is too rigid.

When is iteration actually finished?

Done when
  • Every set is above its threshold
  • Known gaps have owners and timelines
  • Reruns vary by less than 5%
  • No blocking issue remains classified as agent configuration
Not done when
  • Thresholds are met but remaining failures are not understood
  • Scores improved because hard cases were deleted
  • Platform limitations were accepted without documentation

11. Triage: why did it fail, and who acts?

Microsoft's triage framework has four layers: interpret scores (covered above), triage failures, map remediations, then analyse patterns. Every failure resolves to one of three root-cause types — and the type determines the owner.

Root cause typeOwnerMeaning
Evaluation setup issueEvaluation authorThe test case, expected answer or grader is wrong. The agent may be behaving correctly.
Agent configuration issueAgent builderThe agent produced an incorrect response that configuration can fix.
Platform limitationPlatform teamPlatform behavior causes the issue and configuration cannot resolve it.

Pre-triage: check infrastructure health

Before diagnosing anything, confirm the run itself was valid — knowledge sources indexed and reachable, no connector errors, timeouts or rate limits, auth tokens valid throughout, and the evaluation environment matching the intended agent configuration. Triaging an unhealthy run produces confidently wrong conclusions.

Step 0 — prioritize

PriorityTriage firstWhy
1Safety & compliance failuresHighest consequence; must clear before deployment
2Core business scenario failuresDirect hit to the value proposition
3The lowest-scoring setLikely systemic — one root cause may fix many failures
4Failures recurring across runsConsistent failures are easier to diagnose
5Capability scenario failuresImportant, but typically lower impact

With more than ~15 failures, do not triage individually. Start with the weakest set, review a handful by hand, and look for a shared root cause.

Step 1 — verify the evaluation (always start here)

Work these questions in order and stop at the first outcome:

  1. Is the agent's response acceptable anyway? Would a real user be satisfied? → Yes: grader or expected value is wrong.
  2. Is the expected answer current and accurate against the source? → No: outdated expected answer.
  3. Does the test case reflect realistic user input? → No: unrealistic test case.
  4. Could a reasonable alternative also be correct, but the grader disallows it? → Yes: grader too rigid.
  5. Is the evaluation method appropriate for this signal? → No: wrong method. Yes: the evaluation is valid — go diagnose the agent.

Useful heuristics while judging acceptability: same key facts in different words is usually acceptable (grader too rigid); missing critical information that is in the source usually is not; and if "good enough" is genuinely ambiguous, your acceptance criteria are the problem. When unsure, compare against the original source rather than the expected answer.

Validating the grader itself

Grader reliability is a prerequisite for trustworthy triage — an unreliable grader misdiagnoses every failure it touches.

  1. Pick 5–10 cases where you know the correct verdict from manual review.
  2. Run the evaluation and compare grader output to your verdict.
  3. If the grader disagrees on more than 20% of cases, recalibrate it before debugging the agent.

Warning signs: the same case flips verdicts across runs; failures cluster in model-graded sets while deterministic methods pass; the grader flags problems you cannot reproduce by reading the response.

Step 2 — diagnose the agent

Once the evaluation is proven sound, use the activity map and transcript to answer the diagnostic question for the relevant signal.

Step 3 — identify a platform limitation

Suspect the platform when: the same failure survives multiple prompt and configuration variations; retrieval keeps returning wrong documents despite correct source configuration; the model cannot perform the required reasoning despite clear instructions; the orchestration pattern you need is not expressible; or a model-based grader misclassifies consistently despite rubric tuning.

Then: document it, apply a workaround, mark the case as a known limitation (or adjust the threshold so it stops blocking unrelated progress), escalate with evidence, and track it for re-evaluation as the platform evolves.

Multi-turn failures

In conversation sets, the failure often surfaces turns after the root cause. Trace back to the first turn where the conversation diverged. Signals: correct early then self-contradicting; losing a previous tool result; re-asking for information already given; degradation only after 5+ turns (effective context length exceeded).

When it does not fit the framework

Ambiguously-written-but-technically-correct source content, intermittent infrastructure blips, platform model version changes you did not initiate, and genuinely ambiguous test scenarios all resist classification. Record them as unclassified in a failure log with what you observed and what you checked — recurrence usually makes them classifiable.

Check your passes too. Manually review 5–10% of passing cases each run — especially model-graded ones, subjective signals like tone, and cases that flipped to passing after a change. False positives create hidden quality gaps. If you find them, recalibrate the grader.

Every remediation follows the same shape: change X → rerun Y → expect Z. If you cannot state the expected verification, you are guessing.

Treat platform limitations as planning inputs, not defects to tune around — and resist piling on instruction complexity to paper over them.

13. The instruction budget & rerun strategy

Every remediation adds instructions. System prompts have finite effective capacity — past a point the model follows rules inconsistently and previously-solid behavior regresses.

Symptoms of instruction overload
  • Passing cases start failing after unrelated instruction changes
  • Some rules honoured, others silently ignored
  • Fixing one scenario regresses another
  • Failures look inconsistent across similar cases
  • A new, clear instruction has no effect at all
Remedies
  • Consolidate — merge overlapping rules into one well-written paragraph
  • Prioritize — highest-priority instructions first and last; models attend most to those positions
  • Simplify — replace verbose rules with concise ones
  • Externalise — move static lists, policies and reference data into knowledge sources
  • Test holistically — rerun the full suite, not just the affected set

Targeted rerun strategy

What changedWhat to rerun
A single test case (evaluation fix)Only that case
Agent configuration changeThe affected set, plus a spot-check of one unrelated set
System prompt changeThe full suite — prompt changes have broad blast radius
Knowledge source updateKnowledge grounding + factual accuracy sets
Establishing a baselineFull suite, three times

Reserve full-suite reruns for major changes and milestone checkpoints — running everything every time burns time and capacity for little added signal.

Multilingual agents

If your agent supports multiple languages, pick the language for each evaluation run. Three behaviors to know:

  • Query generation defaults to the language you used for the inputs; subsequent runs produce output in the same language as the input.
  • Grader execution — compare meaning detects a language mismatch between expected and actual response and fails the case for language inconsistency.
  • Explainability — in multi-turn conversations, the agent reasons in the same language it responds in.

15. The evaluation checklist

Setting up

  • Sets organized by quality signal, not one giant set per agent
  • At least one set sourced from real production themes, not only generated questions
  • Grader chosen to match each signal — no keyword match (All) on open questions
  • Expected values present on every case using a non-general-quality grader (else: Invalid)
  • User profile set to a realistic end-user identity, not an over-privileged admin
  • Thresholds calibrated to risk profile and written down, with blocking levels named

Operating

  • Baseline established over three runs; average recorded
  • Grader validated against 5–10 manually judged cases (<20% disagreement)
  • Evaluation automated on a schedule and wired into the release gate
  • Results exported before the 89-day window closes
  • 5–10% of passing cases spot-checked each run for false positives

Improving

  • Infrastructure health confirmed before triaging any failure
  • Failures prioritized safety → core business → weakest set
  • Evaluation setup ruled out before touching the agent
  • Each fix stated as change X → rerun Y → expect Z
  • Rerun scope matched to what changed; full suite after prompt changes
  • Platform limitations documented with evidence, not tuned around
  • Instruction budget reviewed — consolidate, prioritize, simplify, externalise
