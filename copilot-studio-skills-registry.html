Copilot Studio Skills & the Microsoft 365 Tools Registry

Where skills are authored, shared, installed, and governed, and how the two experiences fit together. · October 2026

The one thing to remember: Copilot Studio's Skills panel is an agent-level authoring and consumption surface. Microsoft 365 admin center's Agents > Tools > Registry is an organizational tools surface. Related, but not one shared catalog with one lifecycle.

First, check the harness

Microsoft's current Copilot Studio skills documentation applies to agents powered by the GitHub Copilot harness. Skills in this experience are reusable instructions and optional supporting files that help an agent handle a task. They are not the same thing as Azure Bot Service skills used by agents on the standard harness.

Before designing around skills, confirm the agent's harness and verify that the documented skill features are available in your tenant. A skill added to one agent does not, by itself, grant data access or publish the agent to users.

Three surfaces, three jobs

SurfaceWhat it managesThink of it as
Copilot Studio > Build > Skills Create, upload, edit, replace, and add skills to an agent. Sharing and browsing skills through the marketplace are documented as preview features. Agent-level capability and authoring
Microsoft 365 admin center > Agents > Tools > Registry View and govern tools available in the organization. Admins can upload a manifest package, scope access, install it, and manage tool availability. Organization-level availability and governance
Microsoft 365 admin center > Agent registry View and manage agent records. This is an inventory of agents, not a catalog of reusable skill files or tool packages. Agent inventory
Do not collapse these into one registry. A skill shared from Copilot Studio and a skill packaged or uploaded through the admin tools registry have different documented workflows. Do not assume they automatically synchronize, share version state, or appear in every agent-building experience.

Author or add a skill in Copilot Studio

In the documented GitHub Copilot harness experience, open an agent's Build tab and use the Skills component. You can create from blank, generate with AI, upload a skill, or browse marketplace skills where that preview is enabled.

  • Define a narrow job. Give the skill a clear name and a description that says what it does and when the agent should invoke it.
  • Write actionable instructions. Use Markdown, ordered steps, expected output, edge cases, and relevant tool guidance.
  • Choose a file format. Upload a Markdown file with YAML front matter, or a ZIP containing SKILL.md and optional scripts, templates, or reference files.
  • Test the agent. Use Preview to check that the skill is selected for the right requests and that its instructions produce the expected result.

For a skill created from blank, the documented name format uses lowercase letters, numbers, and hyphens. The required name and description help identify the skill and route requests; they are not a substitute for testing.

Share through the Copilot Studio marketplace preview

The documented marketplace flow lets an owner share a skill with specific people or groups in the organization. Other users can browse skills shared with them and add one to an agent. This experience is explicitly marked preview in Microsoft Learn, so treat its availability and behavior as subject to change.

  • After changing a skill that has already been shared, share it again to make the latest version available to the people who already had access.
  • When someone adds a marketplace skill to an agent, the agent receives a snapshot while keeping a reference to the original. Copilot Studio can notify the maker about an available update; the maker chooses whether to update the agent's skill.
  • Sharing the skill is not the same as sharing or publishing the agent. The agent has its own access, deployment, and governance path.

Make a skill available through the admin Tools Registry

Use the Microsoft 365 admin center path when the goal is organizational distribution or governance of an uploaded tool package. The documented upload flow is based on a manifest file; it is not simply the Copilot Studio agent's Save or Share action.

  1. Prepare the skill or plugin package and its manifest. Review which components the package contains, including any skills, MCP servers, or connectors.
  2. In the Microsoft 365 admin center, go to Agents > Tools > Registry and select Upload.
  3. Upload the manifest, review the package contents, and choose whether to scope it to all users or specific users or groups.
  4. Review the configuration and install. Confirm availability using an account in the intended audience and in a supported agent experience.
  5. Plan ownership, access review, updates, and removal before treating the package as a production capability.

The admin Tools page includes registry views and governance actions for tools. The available management actions depend on the item and how it entered the tenant; Microsoft documents controls such as user availability, install or uninstall, block, and deletion of uploaded packages.

Pick the path by the outcome

If you need to...Start hereKeep in mind
Prove an instruction set works on one agent Copilot Studio Build > Skills Confirm the GitHub Copilot harness requirement, then test in Preview.
Reuse a skill with selected makers Copilot Studio skill sharing / marketplace preview Preview feature; sharing the skill does not publish its consuming agents.
Distribute and govern an uploaded package for an organization Microsoft 365 admin center > Agents > Tools > Registry Prepare the manifest, review bundled components, and set the audience deliberately.
Find or govern agent records Microsoft 365 admin center > Agent registry This is about agents, not the skill package catalog.

Govern the capability, not just the file

  • Keep scope intentional. Start with the smallest user or group scope that supports testing; expand only after the skill and its dependencies are reviewed.
  • Review the whole package. Instructions, scripts, templates, MCP servers, connectors, and requested permissions can all affect risk.
  • Use real access controls. Treat skill instructions as behavior guidance, not an authorization boundary. Enforce access to data and actions through the identity, connector, and platform controls behind the agent.
  • Own updates and retirement. Name an owner, track the published version, retest changes, and remove access when the capability is no longer supported.
