Power Platform ALM, Pipelines & Your Wider DevOps Strategy

The ins and outs of application lifecycle management on Power Platform — solutions, environments, pipelines, Dataverse Git integration — and exactly where GitHub and Azure DevOps fit alongside them. Prepared as an enablement reference · July 2026.

The one thing to remember: ALM on Power Platform isn't a single product — it's four moving parts working together: solutions (the unit of change), environments (the stages), source control (the source of truth), and a promotion mechanism (how change moves). Pipelines in Power Platform are the promotion mechanism; GitHub / Azure DevOps are the source of truth and the build system. The mature answer is almost never "one or the other" — it's pipelines for deployment, Git for source control and gates, and pipelines extensibility as the seam between them.

1. The mental model — four moving parts

Unit of change

Solutions

The container that carries your customizations — apps, flows, tables, agents, connectors, PCF controls, plug-ins. Everything downstream of dev moves as a managed solution.

Stages

Environments

Dev → Test/QA → UAT → Prod, each with its own Dataverse database, security, and data. Environment strategy is your release strategy.

Source of truth

Source control

Git — via native Dataverse Git integration, or via pac CLI export/unpack in a build workflow. Branches, PRs, history, and rollback live here.

Movement

Promotion

Pipelines in Power Platform (in-product, maker-friendly, governed) and/or GitHub Actions / Azure Pipelines (code-first, cross-tenant, fully scriptable).

If any one of these is missing, you feel it immediately: no solutions means untracked drift; no environment separation means editing in production; no source control means the maker's environment is your backup; no promotion mechanism means someone is hand-carrying zip files.

2. Solutions — the fundamentals people skip

ConceptWhat it means in practice
UnmanagedThe editable, in-development form. Lives only in development environments. This is what you commit to source control.
ManagedThe built, locked artifact you deploy to test/UAT/production. Not editable in place — which is exactly the point. Uninstalling removes its components cleanly.
Publisher & prefixChosen once, effectively forever. Set a real publisher with a meaningful prefix (not new_) before you create your first table or column.
LayeringMultiple managed solutions can touch the same component; the resulting behavior is resolved by layer order. In the target environment you can inspect layers and diff between them.
Connection referencesDecouple a flow from a specific connection so each environment binds its own. Non-negotiable for clean promotion.
Environment variablesPer-environment configuration (URLs, IDs, toggles) supplied at deployment time instead of hard-coded.
What solutions do not carryDataverse data. Reference/config data needs a separate mechanism (e.g. the Configuration Migration tool or a data-seeding step in your build).
Anti-pattern: the single giant "Company Solution" that everything lands in. It grows into a slow, all-or-nothing deployment with cross-team blast radius. Split by product/domain, keep shared components in a dedicated base solution, and be deliberate about dependencies between them.

3. Pipelines in Power Platform — what they actually are

Pipelines bring CI/CD into the product itself. An admin configures a pipeline once; from then on a maker deploys their solution from inside their development environment in a few clicks — no exports, no zip files, no knowledge of ALM tooling required. Developers can drive the same pipelines from the pac pipeline command group.

The architecture

  • A pipelines host — a Dataverse environment that stores pipeline configuration, run history, and every exported solution artifact. It should be a production environment, but it does not need to be a managed environment.
  • Environment records — each environment is registered against the host and classified as Development or Target. An environment can only belong to one host.
  • Stages — the ordered hops (e.g. Dev → QA → UAT → Prod). Solutions traverse them sequentially; skipping isn't possible.

Platform host vs. custom host

Zero setup

Platform host (personal pipelines)

Provisioned automatically the first time anyone in the tenant opens the Pipelines page. Great for getting a maker off manual export/import today.

  • Max three environments — one dev, two targets.
  • Can't be shared with other users.
  • Can't be extended (no approvals, no delegated deployment).
Enterprise

Custom host (governed pipelines)

A dedicated Dataverse environment you stand up and administer via the Deployment Pipeline Configuration app.

  • Unlimited stages and environments.
  • Shareable across teams.
  • Fully extensible — approvals, delegated deployments, custom gates.
Watch this trap: an environment can only be associated with one host. If makers create personal pipelines on the platform host first, those environment records must be deleted from the platform host before the environments can join your governed custom host. Set a default pipelines host early if you want to steer everyone to the governed path from day one.

What pipelines deploy — and what they don't

Behavior
DeploysThe solution plus target-environment configuration: connections, connection references, and environment variables — validated up front, before the deployment starts.
BackupsBoth managed and unmanaged artifacts are exported and retained in the host for every deployment.
Tamper-proofingThe solution is exported once, when the maker hits Deploy. The same artifact is promoted through every subsequent stage — nothing can bypass QA or an approval gate.
Import behaviorDefaults to Upgrade without Overwrite customizations. Not currently configurable per deployment.
RollbackRedeploying a previous solution version is supported when the pipeline setting is enabled; otherwise only higher versions can go out.
Not supportedCross-tenant deployment · unmanaged deployment to non-dev · multiple solutions in one deployment · Power BI dashboards/datasets (preview) · Dataverse table data.

Roles

  • Deployment Pipeline Makers — can create and consume personal pipelines managed in the custom host.
  • Deployment Pipeline Users — can run pipelines shared with them; read access to stage runs in their business unit.

4. Making pipelines enterprise-grade: gates and extensibility

Out of the box a pipeline is a straight run. Extensibility lets you insert your own stops on the track — implemented as Power Automate cloud flows in the host environment, triggered by Dataverse business events. The maker experience stays a single Deploy button no matter how sophisticated the machinery behind it.

1

Pre-export step

Custom validation the moment a deployment is requested — solution checker results, naming standards, a change-record lookup. Nothing is exported from dev until your logic says go. Enable on the first stage only.

2

Delegated deployment

The deployment runs as a service principal or the stage owner rather than the requesting maker — so makers need no access at all in production. Requires approval from an authorized identity. This is the single highest-value control for securing prod.

3

Pre-deployment step

A final gate after approval and before the import — change-window checks, CAB sign-off, a freeze calendar, notifying a system of record.

Each step raises real-time triggers you can subscribe to in cloud flows: OnDeploymentRequested, OnApprovalStarted, OnApprovalCompleted, OnPreDeploymentStarted, OnPreDeploymentCompleted, OnDeploymentStarted, OnDeploymentCompleted. Your flow signals back with an unbound action (UpdatePreExportStepStatus, UpdateApprovalStatus, UpdatePreDeploymentStepStatus) using status 20 to complete or 30 to reject, with comments surfaced to the maker in run history.

Use Power Automate trigger conditions so a flow only fires for the pipeline or stage it governs — e.g. @contains(triggerOutputs()?['body/OutputParameters/DeploymentStageName'], 'QA'). This keeps flow runs (and request consumption) down.

Remember: personal pipelines on the platform host can't be extended. Gates only exist on a custom host.

5. Source control: Dataverse Git integration

Native Git integration syncs unmanaged solutions and solution objects between Dataverse development environments and a Git repository, directly from the solutions experience in make.powerapps.com — no CLI required for the maker.

  • Dev environments only. Git integration is designed for development. Test and production still receive built managed artifacts, deployed by pipelines.
  • Human-readable file format. Solution objects are stored so changes are diffable, and objects are stored once and shared across solutions in the same repo/folder rather than duplicated.
  • Short-lived dev environments. Because source control holds the truth, you can rehydrate a dev environment from a branch on demand and tear it down after — less sprawl, less storage, fewer stale environments.
  • Fusion teams. Makers and pro devs work in separate environments and converge through the repository.
  • Recovery. Restore to a previous state after an unintended change.
Provider support (rechecked August 2026): native Dataverse Git integration works with Azure DevOps Git repositories only. The setup documentation still lists an Azure DevOps subscription and project as a hard prerequisite, and there is no GitHub option in the Connect to Git flow. GitHub as a native Git provider was on the 2026 wave 1 release plan with public preview indicated for August 2026, but it has not appeared in the product documentation as of this review. Treat it as announced-but-unshipped and do not architect around it until Microsoft Learn documents it. GitHub users reach the same outcome today through pac CLI export/unpack inside a GitHub Actions workflow.

The code-first caveat worth knowing

If a developer deploys a PCF control or plug-in directly into an unmanaged solution in a maker environment and then commits, only the built artifact (the DLL, the bundled JS) lands in source control — so you end up with the binary and the source both in the repo, able to drift apart. The recommended pattern is to build code-first components in a proper build process, produce an unmanaged solution, and import that into the maker environment. Source code stays the single source of truth.

6. Where GitHub fits

GitHub Actions for Microsoft Power Platform is a first-party action set on the GitHub Marketplace that removes the need for custom scripts. Actions fall into four categories — helper, quality check, solution, and environment management — and cover:

  • Export/import and pack/unpack of solutions between environments and source control.
  • Deployment to downstream environments.
  • Provisioning and de-provisioning environments (including spinning up ephemeral build environments).
  • Static analysis via Power Apps solution checker as a PR quality gate.

Authentication is via service principal + client secret (supports MFA) or username/password (does not). Actions run on Windows or Linux runners, require a Dataverse environment with a database, and carry no extra license cost beyond your GitHub plan.

Microsoft's own guidance is unambiguous: use pipelines for core deployment, and extend them to integrate with other CI/CD tools where needed. Doing so usually makes the workload inside GitHub or Azure DevOps smaller and cheaper to maintain, not larger.

7. A reference pattern that scales

Microsoft's enterprise ALM reference architecture combines Dataverse Git integration, a custom pipelines host, and repo-side governance. Distilled:

Development

  • Map each development stream (DEV1, DEV2, DEVn) to its own environment and feature branch.
  • Sync changes into Git through Dataverse Git integration.
  • Merge feature branches into main via pull requests with branch protection.
  • Pull main back down into every dev branch to avoid drift. main is the authoritative source for release promotion.

Test & UAT

  • Promote from main into Test using a custom pipelines host with the Source Control deployment type — deploying from the repo, not from a maker's environment.
  • Technical validation and smoke testing in Test; promote to UAT with pipelines and cut a release branch.
  • Generate release notes from work items and distribute for business validation.

Production & hotfix

  • Promote approved UAT changes to Production through the same pipeline, with approvals and service-principal execution.
  • Handle urgent fixes in a dedicated hotfix environment connected to the current release branch.
  • Promote the hotfix through the controlled pipeline, then merge the release branch back into main so the fix survives the next release.

8. A maturity ladder — pick your rung, then climb

LevelWhat it looks likeMove up when…
0ManualExport/import zips by hand, or worse, editing in production.Immediately.
1Personal pipelinesPlatform host, one dev + two targets, maker self-service.You need approvals, sharing, or more than three environments.
2Governed pipelinesCustom host, shared multi-stage pipelines, managed targets, admin-owned.Production needs segregation of duties.
3Gated pipelinesDelegated deployment via service principal, approval flows, pre-deployment gates, run analytics.You need history, review, and rollback beyond the host's artifacts.
4Source-controlledDataverse Git integration, branch-per-stream, PR review, short-lived dev environments.You have pro-code components or cross-tenant/multi-solution releases.
5Full CI/CDGitHub Actions builds and quality gates feeding pipelines for governed promotion; release notes and work-item traceability automated.—
Don't skip rungs to look sophisticated. A team that adopts level 1 this week and actually uses it beats a level-5 design nobody can operate. The whole point of pipelines is that the maker experience stays identical as the machinery behind it matures.

9. Pitfalls checklist

  • Default environment as the pipelines host. Supported, not recommended. Stand up a dedicated host.
  • Host doubling as a dev environment. Not supported.
  • Publisher prefix left as new_. Fix it before the first table exists — it's effectively permanent.
  • Hard-coded connections. Use connection references and environment variables or every deployment needs manual post-processing.
  • Unmanaged solutions in production. Always deploy managed downstream; unmanaged belongs in dev and source control only.
  • Unpublished customizations. Pipelines don't publish before export — publish as you save.
  • Cross-geo assumptions. Host and environments must share a geography unless cross-geo solution deployments are enabled on the host.
  • Rollback disabled. Turn on redeploying previous versions before you need it, or you're editing solution.xml by hand at 2am.
  • One dev environment per solution. Pipelines assume a single dev environment per solution; multi-dev parallelism needs Git integration and branches.
  • Binaries and source both in the repo. Build code-first components properly and import the resulting solution.
  • No retention policy. Every deployment stores artifacts in the host — configure bulk delete jobs.
