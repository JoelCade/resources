Microsoft Power Platform · Preview Capability Guide

Managed Apps in Power Platform (Preview)

What the AI-generated, vibe-coded app experience became once it grew up: a real CLI, a real deployment pipeline, and real platform governance around your own code. How to build one, how to manage it, and what it actually costs. · September 2026.

The one thing to remember: Managed Apps is not a new app designer and not a new license. It is the managed hosting and lifecycle layer Power Platform wraps around a web application you (or a coding agent) wrote. You keep the code, the framework, and the repository. The platform supplies Microsoft Entra identity, connector-brokered data access, DLP, sharing limits, Conditional Access, telemetry, and deployment. Commercially it behaves like a code app: end users need a Power Apps Premium license to run it, and everything the app touches is licensed and metered as it always was.

1. Where this came from, and why the name changed

There have been three overlapping names for closely related ideas over the last year, and mixing them up is the fastest way to give a customer the wrong answer.

NameWhat it actually isStatus
Power Apps vibe
the "vibe-coded apps" experience		 A browser-based, AI-native workspace at vibe.powerapps.com. You describe a business problem in natural language and it produces a plan, a data model, and a generated app together. The generated artifact was already code, not a canvas app. Preview. Microsoft now points makers toward app building in Copilot Cowork and Copilot Studio, and vibe apps can be converted and downloaded as code.
Power Apps code apps The code-first counterpart: you build a React, Vue, or similar web app in your own IDE, wire it to connectors, and publish it into a Power Platform environment with the Power Apps CLI (pa). This is the runtime and governance model the vibe output lands on. Preview, with published documentation, an admin enablement toggle, and a documented managed-platform capability matrix.
Managed Apps
the subject of this page		 The productized version of that same idea, with its own first-party toolchain: the ms CLI, an SDK, a Vite plugin, official project templates, a coding-agent plugin, and GitHub Actions for CI/CD. Same platform promise, a proper lifecycle around it. Public preview. APIs, templates, and tooling may change before general availability.
Say this to a customer, not more than this: "It is the same idea you saw demoed as vibe coding, now with a supported CLI, templates, source control, and a deployment pipeline. It is in public preview, so treat tooling and APIs as subject to change and do not put a tier-one production workload on it yet."

What you keep, and what the platform takes over

You own

The application

  • The framework choice — React and TypeScript on Vite in the first-party template.
  • The UI, the state, the business logic, the tests.
  • The repository, the branches, and the review process.
  • Which data sources the app binds to, and which operations it is permitted to call.
Platform owns

Everything around it

  • Microsoft Entra authentication and authorization on every session.
  • Connector brokering to 1,500+ data sources, callable from TypeScript.
  • DLP enforcement, sharing limits, app quarantine, tenant isolation.
  • Hosting, deployment, versioning, and operational health telemetry.

2. Architecture: the four pieces that matter

Toolchain

The ms CLI

Published to the public npm registry as @microsoft/managed-apps-cli and installed globally so the ms binary is on your PATH. It scaffolds, runs the local dev loop, adds data sources, builds, packs, uploads, deploys, shares, and manages auth. Companion packages supply the SDK (@microsoft/managed-apps) and the Vite plugin.

Config

ms.config.json

The per-app manifest written by ms app create. It records the app ID, the environment ID, the repository mode, and every connection reference the app binds to — including the runtime action policy for shared connections. This file is the contract between your repository and the service.

Repository mode

Platform-managed or bring-your-own

Apps are created either against a platform-managed Git repository, or in BYOB mode with ms app create --repo none, where you keep the code wherever you already keep code and the CLI uploads a built artifact instead. The mode drives how deployment works, so decide it on day one.

Runtime

The App Player

Local development runs the app in the App Player with hot reload, against real connectors and real environment data. There is no "mock mode" to drift away from — what you test locally is what the platform brokers in production.

3. Building one

Prerequisites

  • Node.js LTS (v22 or higher for the managed apps toolchain) and Git, with Git credentials configured. On Windows, Git Credential Manager handles the first interactive authentication against the platform repository endpoint.
  • An environment with code apps enabled. An admin turns this on per environment, or at scale with environment groups and rules.
  • For the AI-assisted path, a coding agent CLI — GitHub Copilot CLI or Claude Code — with its own subscription, plus the Microsoft-published plugin.
  • Not the default environment. The AI app-building experiences are excluded there, and the default environment is the wrong place for this work anyway.

The agent-assisted path

1

Install the plugin once

From inside a Copilot CLI or Claude Code session, register the Microsoft marketplace and install the plugin. It is available in every project folder afterward.

/plugin marketplace add microsoft/Managed-Apps
/plugin install microsoft-managed-apps@Managed-Apps
2

Describe the app in an empty folder

Run /create-app. The agent installs the CLI globally with your confirmation, asks what you want to build in plain language, scaffolds the project with ms app create, and starts the local dev server. Nothing reaches the cloud at this point.

Be specific about users, data, and the tasks the app performs. A vague prompt produces a generic app you then spend longer correcting than you would have spent writing the prompt properly.

3

Bind data sources deliberately

Each binding runs ms app add data-source against a connector, regenerates typed TypeScript services, and hot-reloads them into the running app. Add what the app needs and no more — every binding is a governance surface and a licensing question.

Dataverse SharePoint Excel OneDrive Outlook Teams Azure DevOps Copilot Studio agents Any other connector
4

Iterate locally, not in production

The inner loop is ms app dev, not deploy. Local dev does not validate connection policies, so it stays fast; the validation gate fires at pack and deploy time instead.

5

Build, commit, then deploy

The toolchain enforces a discipline worth keeping even when it does not: build must succeed, changes must be committed and pushed, and only then does ms app deploy run. Git-backed deployments are guarded when the working tree is dirty or local main is ahead of origin/main.

The rule that trips up every developer once: managed apps run in a sandbox that does not permit arbitrary outbound network calls. A raw fetch to Microsoft Graph, Azure REST, or any third-party API will work in nobody's production environment. If a connector exists, use the connector. If no connector covers the capability, the honest answer is that the scenario is not supported yet — not that you should write a direct call as a workaround.

The code-first path

You do not need an AI agent in the loop. Install the CLI, scaffold from the template, and work in your IDE:

npm install -g @microsoft/managed-apps-cli
ms auth login
ms app create --display-name "Field inspection log" --repo none
npm install
ms app dev            # local App Player with hot reload
ms app deploy         # build, pack, upload, deploy
ms app share <app-id> --access edit

Useful command families: ms app for the lifecycle, ms connector to discover connector actions in the environment, ms auth for sign-in and account switching, and ms telemetry to control CLI telemetry. Global options include --environment-id, --cloud for sovereign clouds, --non-interactive, and --json.

4. Shipping it: CI/CD and release control

Interactive sign-in is fine for a developer laptop. It is not available on a build runner, so continuous deployment runs as a service principal. Microsoft publishes three GitHub Actions for this.

ActionWhat it does
install-ms-cliInstalls the ms CLI on the runner.
ms-app-packRuns ms app pack — builds and packs the app into a deployable artifact. Optional, since deploy can pack internally.
ms-app-deployRuns ms app deploy — builds, packs, uploads, and deploys to the target environment, returning the app ID, commit, and play URL.

Pin to the moving major version (@v1) for ongoing fixes, or to an immutable @v1.x.y when you need a fixed rollback point.

Three prerequisites that cause most first-time CI failures

  1. A service principal with the right role on the target environment. System Administrator plus System Customizer for Dataverse-enabled environments; Environment Admin for non-Dataverse environments. All three of app ID, client secret, and tenant ID must be supplied, or the action falls back to an interactive flow that cannot complete on a runner.
  2. AllowExternalArtifactDeployment enabled on the environment by a tenant administrator. Without it, bring-your-own-repository deploys fail with an explicit "external artifact deployment is not enabled" error. This is a deliberate admin gate, not a bug — it is the control that decides whether externally built artifacts may enter the environment at all.
  3. Deployment mode matches the repository mode. BYOB apps deploy an artifact; platform-managed and GitHub-backed apps deploy a specific commit.
Preview gate worth adopting as policy: the preview build pipeline currently builds only from main. Feature branches cannot be previewed. Decide early whether that fits your branching strategy, because the workaround is either landing changes on main first or skipping the preview entirely — and one of those is a governance decision, not a developer convenience.

5. Managing and governing them

This is the strongest argument for the capability and the part most demos skip. A managed app inherits the same managed-platform controls as a canvas app, with a few documented exceptions.

ControlApplies?Notes
Microsoft Entra authenticationYesEvery user session authenticates against Entra ID. There is no anonymous mode.
Data loss prevention at launchYesConnector policy is enforced when the app launches, the same as canvas apps.
Sharing limitsYesFollows Managed Environments canvas app sharing limits.

Admin enablement, in order

  1. Power Platform admin center → Manage → Environments → the target environment → Settings → Product → Features.
  2. Turn on the code apps feature toggle, then save. Use environment groups and rules to apply this across many environments rather than clicking through each one.
  3. If external artifact deployment is required for your CI pattern, have a tenant admin enable AllowExternalArtifactDeployment on that environment.
  4. For the AI-assisted building experiences, confirm the relevant Copilot tenant settings are on, and consider enabling external models at the environment level where higher generation quality matters.

Content Security Policy is stricter than people expect

Generated apps enforce a platform-level Content Security Policy that restricts which origins the app may load content from. This protects users against cross-site scripting and content injection, but it also means external images and external content are blocked in published apps, and the policy cannot be customized per app, per environment, or per tenant. If a converted app suddenly shows broken images, this is almost always why — the fix is to allowlist the specific content-delivery origins in the target environment's code app CSP configuration, where that is permitted, or to host the assets inside the app bundle.

6. Shared connections and least privilege

This is the single most important governance detail in the capability, and it has no equivalent in canvas apps.

When a connection reference is shared, the same connection can back several apps and it carries the full permissions of whoever created it. Left unrestricted, an app that only needs to read a list could delete from it. Managed Apps closes that gap by requiring each app to declare, in ms.config.json, the connector operations it is allowed to invoke. The Connectors infrastructure enforces that limit per app, so two apps sharing one connection get two independent policies.

Reference shapeWhat you declareVocabulary
Tabular — has dataset tables A non-empty list on every table. A connector-level declaration does not satisfy the tables. get, post, patch, delete
Action connector — no dataset tables A connector-level list of action IDs the app actually calls. Action IDs from ms connector list-actions, allowed behaviors only
Not shared Nothing. Do not add the declaration where it does not belong. —

Three things make this bite in practice:

  • Nobody opts in. The CLI writes the shared-connection marker automatically whenever the connector's authentication type is shareable. An ordinary data-source add can produce a shared reference with no one asking for it. Read the config back after every add.
  • It fails the deploy, not the dev loop. Validation runs at pack and deploy. A missing declaration surfaces late unless you check for it deliberately.
  • Granting everything passes validation and protects nothing. Declaring every verb or every action satisfies the schema while removing the entire point of the policy. Infer the set from what the code actually calls, and have a human confirm it.
Never do this: removing the shared-connection identifier from the config to get past a validation failure. That field records how the connection was genuinely created; deleting it misrepresents the binding to every future reader and to the platform. Declare the operations instead.

7. Licensing and cost

Headline: there is no separate "Managed Apps" SKU. The app itself is licensed like a Power Apps code app — every end user who runs it needs a Power Apps Premium license. Everything the app consumes is licensed and metered exactly as it would be from any other app.

What you are actually paying for

Cost lineWho paysWhat drives it
Power Apps Premium (per user, per month) Every end user who plays the app Headcount. This is the dominant line for any app with a real user base, and the one to model first.
Dataverse capacity Tenant Database, file, and log storage if the app stores data in Dataverse. Entitlements accrue from licenses; overage is purchased.
Managed Environments Tenant, via premium licensing Several governance controls listed above — sharing limits in particular — are Managed Environments features. If you are relying on them, the environment has to be managed, which requires premium licensing for its users.
Coding agent subscription The developer or the engineering org GitHub Copilot or Claude Code, if you use the agent-assisted build path. This is a developer tooling cost, not a Power Platform meter, and it is charged per developer rather than per app user.
Copilot Credits Tenant Only if the app itself consumes metered AI at runtime — for example invoking a Copilot Studio agent through a connector. Generating the app is a build-time activity; calling an agent every time a user clicks a button is a per-transaction meter. Do not conflate the two.
Premium and custom connectors Covered by Power Apps Premium Included in the premium entitlement, but each binding is still a DLP and data-residency decision.
Downstream service costs Varies Whatever sits behind the connectors — Azure services, third-party SaaS, Dynamics 365 — is licensed on its own terms and is frequently the largest surprise.

The cost mistakes worth pre-empting

  • "It is just code, so it must be cheaper." Writing the app got cheaper. Running it did not. A hundred users still means a hundred Power Apps Premium licenses, and an AI-generated prototype produced in an afternoon carries the same per-user run-rate as one that took a quarter to build. The generation cost is the small number.
  • Prototype sprawl. When the cost of producing an app collapses, the number of apps does not stay flat. The governance problem arrives before the licensing problem, and both arrive faster than they did with canvas apps. Decide where prototypes live, how long they live, and who is allowed to promote one to a licensed user base.
  • Counting AI generation as a runtime meter. Building the app with a coding agent bills against the developer's agent subscription. It does not consume Copilot Credits for each end user. Confusing these produces a forecast that is wrong by an order of magnitude in either direction.
  • Forgetting the governance dependency. Several of the controls that make this capability defensible are Managed Environments features. If the plan assumes those controls, the licensing model has to assume premium.
  • Pricing a preview. Preview terms are not production terms. Confirm current licensing against the Power Platform Licensing Guide and the published pricing page before putting a number in a proposal.

8. When to reach for this, and when not to

SituationBetter answer
A bespoke UI that canvas cannot express, or a design system the business insists onManaged app. This is the scenario it exists for.
A development team that already works in React, Git, and pull requests, and finds canvas authoring alienManaged app. It meets them where they are while keeping the governance.
A rapid prototype to prove a business problem is worth solvingManaged app, with an explicit end date and an explicit promotion decision.
Standard forms over Dataverse, with business process flows and a records-management patternModel-driven app. You would be rebuilding an enormous amount of supplied behavior.
A straightforward internal task app that a maker can own and maintainCanvas app. Lower ceiling, but far lower support burden and no build pipeline.
An external or anonymous audiencePower Pages. Managed apps authenticate every user through Entra ID.
A conversational interface, or an agent that reasons over knowledgeCopilot Studio. A managed app can call an agent through a connector, but it is not an agent.
A tier-one production workload with a hard go-live date this quarterWait, or use a generally available option. This is public preview, and tooling and APIs may change before general availability.

9. Rollout checklist

Before the first app

  • Pick a non-default environment in a supported region and enable code apps on it.
  • Decide the repository mode — platform-managed or bring-your-own — and stay consistent inside a portfolio.
  • If CI is in scope, create the service principal, grant it the correct environment role, and have an admin enable external artifact deployment.
  • Confirm the DLP policy that applies to the environment, and check it against the connectors the apps are expected to use.
  • Agree who pays for Power Apps Premium, and at what user count the business case is reviewed.

Per app

  • Read ms.config.json back after every data-source add and check whether the reference became shared.
  • Declare least-privilege operations for every shared reference, and have a human confirm the list rather than accepting an inferred one silently.
  • Verify the build succeeds and the branch is pushed before any deploy.
  • Test the published app, not just the local one — Content Security Policy and connector consent behave differently there.
  • Share deliberately, and remember that sharing limits apply.

Ongoing

  • Watch operational health metrics in the admin center alongside your own application telemetry.
  • Re-check the declared operation policy whenever a table or connector is added — a new table invalidates the config and fails the next deploy.
  • Keep a register of which prototypes are still alive and which have earned a licensed user base.
  • Re-read the preview terms at each toolchain upgrade. In public preview, the contract moves.
