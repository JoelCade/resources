Power Platform Licensing & Managed Environments

A plain-language overview of how Power Platform is licensed, and what changes when you turn on Managed Environments. Prepared as an enablement reference · Updated August 2026.

The one thing to remember: A Managed environment is a premium capability. Once you manage an environment, every user with active usage in it must hold a standalone premium license (Power Apps Premium, Power Automate Premium, Copilot Studio, Power Pages, or a qualifying Dynamics 365 plan) — or the environment must have qualifying pay-as-you-go meters / per-app capacity allocated.

1. The core distinction: “seeded” vs “premium”

Most licensing confusion comes down to this split. What a user can build and run depends on which bucket their license falls into.

Seeded (bundled)

Included with Microsoft 365 / Dynamics 365

  • Build apps & flows on Microsoft 365 data and standard connectors only.
  • No premium/custom connectors.
  • No on-premises data.
  • D365-seeded rights apply only within the context of that Dynamics 365 app.
Premium (standalone)

Power Apps / Power Automate Premium, Copilot Studio, etc.

  • Premium & custom connectors.
  • On-premises data gateway access.
  • Create Dataverse in non-default (production/sandbox) environments.
  • Includes Managed Environments as an entitlement.

3. What “Managed Environments” actually gives you

Managed Environments are a suite of premium governance capabilities that let admins manage Power Platform at scale — more control, less effort, more insight. You can apply it to any environment type, and it’s toggled per environment (not all-or-nothing across the tenant).

Capability by capability: what actually changes when you turn it on

The list above is easy to mistake for a feature bundle you switch on. It is more precise to read it as a set of admin controls that do not exist at all in an unmanaged environment, plus a few existing capabilities that gain enforcement or scope. The tables below give the before-and-after for each.

Governance and control at scale

Note this creates managed developer environments by default, which brings the licensing rule in section 4 with it.

A note on sharing limits that catches people out: the rules apply when someone tries to share, not retroactively. Users who already had access keep it. If an app, flow or agent is out of compliance after you set the rules, the only sharing action allowed is unsharing until it complies. Allow up to an hour after saving before enforcement begins.

Be precise about data policies when you are in front of a customer. Data loss prevention is not a Managed Environments feature. DLP policies can be created and enforced across unmanaged environments too. What Managed Environments adds is visibility — the ability to see which policies land on a given environment — plus data policies for desktop flows. Selling DLP itself as a managed-only benefit is the single easiest way to lose credibility on this topic.

Read as a whole, the pattern is consistent: Managed Environments is where the enforcement and tenant-scale versions of Power Platform governance live. Almost everything on these lists is either impossible without it, or exists only in an advisory form that nobody is obliged to act on.

Dataverse long-term data retention is now Managed-Environment-only

Dataverse long-term data retention — the archival capability that moves inactive rows out of the live database into a compressed, read-only retention store — is gated on Managed Environments. Microsoft states that the Power Platform environment where the retention policy resides must be a Managed Environment.

What happens if the environment is not managed: you can still create data retention policies, but the policies are disabled and will not run. This applies to Dynamics 365 customers too, who are required to upgrade the environment to a Managed Environment if it is not one already. Verified against Microsoft Learn on 25 August 2026.

This matters commercially because archival is usually pitched as a storage cost conversation, not a governance one. Data moved to long-term retention is compressed by roughly 50 percent on average, so it is a genuine lever on Dataverse database capacity spend. But reaching that lever now requires the environment to be managed, which in turn triggers the premium licensing rule in section 4 for every user with active usage in it. Price the two together, not separately.

Two practical notes when scoping this: file and image attachments are retained but do not deliver capacity savings, and audit tables and elastic tables are not currently supported for long-term retention.

4. The licensing rule for Managed Environments

When you enable Managed Environments in an environment, all active usage requires a qualifying standalone license or PAYG meter. In practice:

  • Every user running an app in a managed environment needs Power Apps Premium, Power Automate Premium, or a qualifying Dynamics 365 Enterprise license (or per-app capacity allocated to the environment).
  • Every user running a cloud flow in a managed environment needs the same (or Flow per-business-process capacity allocated).
  • A single user who runs both an app and a flow does not need two licenses — either Power Apps Premium or Power Automate Premium satisfies the requirement.
  • Flows triggered within an app or agent are covered by that app’s / Copilot Studio license.
  • Trial licenses can cover users in managed environments, but trial restrictions (e.g. 30-day) still apply.
The trade-off: Managed Environments = ease of administration & governance vs. the cost of premium licensing for the users in those environments. A common pattern: leave the default environment unmanaged for citizen makers (locked-down DLP, no premium), and reserve managed environments for a smaller community of enterprise builders who hold premium licenses.

Creating is free, running is not — and that distinction is narrower than it sounds

Creating or previewing an app or flow in a managed developer environment requires no premium license. A premium license is required to run one. Microsoft states this plainly, and the prerequisites for environment routing put it more bluntly still: users in a managed developer environment must have premium licenses to run Power Platform assets.

The catch that reverses the conclusion: “running” includes makers running their own apps and flows. The Power Apps Developer Plan guide is explicit that users, including makers running their own assets, need a premium license in addition to the Developer Plan to run anything in a managed developer environment. So the free part is genuinely just authoring and previewing. Anyone who actually uses what they built needs a license.

This matters most for the scenario it looks tailor-made to solve. If your security team has mandated that nothing may live in the default environment, routing every maker into a personal managed developer environment does not sidestep the licensing cost for personal-productivity makers. It creates it: the migration is free, the ongoing use is not.

The established pattern runs the other way. Keep personal-productivity makers in a locked-down environment with strict data policies and no premium entitlement, and reserve managed environments for the smaller population of enterprise builders who hold premium licenses. Treat a no-default mandate and the managed-environment licensing model as a genuine trade-off to be reconciled, not a problem that routing solves for free.

One nuance worth keeping straight: non-managed developer environments do not carry this requirement. But environment routing creates managed developer environments by default, so the moment you adopt routing you have adopted the licensing rule along with it.

“We have Microsoft 365 Copilot, so we’re covered” — the common trap

Copilot Studio for Microsoft 365 Copilot is a qualifying entitlement, but the qualification matters: it covers Copilot Studio features only. It is a per-workload rule, not a per-environment one. In a managed environment:

WorkloadIs a Microsoft 365 Copilot license enough?
Copilot Studio agents used in Microsoft 365 Copilot, Teams or SharePointYes
Standalone Copilot Studio agent (own channels, premium connectors)No — requires standalone Copilot Studio
Running a Power AppNo — requires Power Apps or Power Automate Premium
Running a Power Automate cloud flowNo — requires Power Apps or Power Automate Premium

Guidance that flattens this into a single “you need a premium Power Platform license or a Microsoft 365 Copilot license” is the usual source of confusion. Ask which workload is being licensed, not which environment.

Compliance notifications are now live

The licensing requirement itself is not new, but Microsoft now surfaces non-compliance proactively rather than silently:

  • From March 2026 — administrators are notified through the Microsoft 365 Message center and the Power Platform admin center.
  • From April 2026 — recommendations appear under Actions → Recommendations identifying affected users.
  • From June 2026 — end users see in-app notifications when they open an app in a managed environment without an appropriate license, escalating from informational to warning to error at seven-day intervals. Users can request a license directly from the notification.

To audit your own position, download the “Users requiring licenses in Managed Environments” report from Licensing → Power Apps → Summary → Download report. Note that it only lists users who actually launched an app in the selected month. Enabling an auto-claim policy in the Microsoft 365 admin center can pre-empt the issue entirely, provided you hold sufficient license capacity.

5. Per-user vs per-app: which is cheaper?

Rule of thumb: if a user actively uses ~10 or more apps, a per-user license is usually the better value. Below that, per-app licensing (allocated to the environment) tends to win. Model both against your actual usage — the break-even shifts with your mix.

6. Copilot Studio note

Copilot Studio has its own consumption model (Copilot Credits / PAYG) layered on top of environment licensing. Key nuance for agents:

  • An M365 Copilot-licensed user interacting with an agent in an authenticated chat burns no Copilot Studio credits — their license covers it.
  • Autonomous agents (triggered by schedule, email, or a file drop) have no license coverage and always consume Copilot Studio credits.
  • A Copilot Studio agent requires a Dataverse-enabled environment.

7. Quick self-check

QuestionWhere it points
Do makers need premium/custom connectors, on-prem data, or their own Dataverse?Premium standalone license.
Do you want governance at scale (grouping, routing, DLP, pipelines, insights)?Turn on Managed Environments — on the specific environments that warrant it.
Who consumes in a managed environment?Each active user needs a qualifying premium license (or allocated per-app/PAYG capacity).
Unpredictable or spiky usage / production safety net?Attach pay-as-you-go via an Azure subscription.
