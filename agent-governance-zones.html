Zoned Agent Governance

How to administer AI agents across Microsoft 365 Copilot, Copilot Studio and Power Platform without either blocking the business or losing track of what got built. The three-zone model, the controls that implement it, and where each one is administered. · August 2026

The one thing to remember: agent governance is not a single switch. It is a set of policy tiers — zones — where the strength of the control matches the blast radius of the agent, not the enthusiasm of the person building it. A personal agent grounded in files someone already has access to needs almost nothing. An agent that writes to a system of record on behalf of thousands of people needs everything. Most governance failures come from applying one of those settings to both cases.

1. What a zone actually is

A zone is a level of risk, expressed as a set of environments with matching policy. It is not a product, a license or a feature you turn on. Microsoft describes three, and they map cleanly to who is building, what the agent can reach, and how far it can spread.

Zone 1

Citizen development

Anyone can build personal or small-team agents grounded in content they already have access to. Agents are read-only and stay private to the maker.

Agent Builder SharePoint agents Developer environments
Zone 2

Partnered development

Trained makers build for other teams and departments with a wider set of capabilities, under a review process and inside environments that IT provisions and manages.

Copilot Studio Managed environments Pipelines
Zone 3

Professional development

Professional developers and IT build mission-critical agents to organizational ALM standards, with the strongest security controls and, often, a service level agreement behind them.

Copilot Studio Foundry Agent Service ALM

The zones are cumulative in rigor, not exclusive in tooling. Copilot Studio appears in both Zone 2 and Zone 3; what changes between them is the environment the agent lives in, the review it passes through and the identity it runs as.

2. The three zones side by side

The default environment is not Zone 1. It is a shared, tenant-wide space that everyone lands in by default, which makes it the single worst place for personal experimentation. Zone 1 means a personal developer environment per maker, provisioned automatically, isolated by design. Leaving personal building in the default environment is how organizations end up unable to answer "who owns this agent and what can it see?"

3. Policy, process and people come before the switches

The platform controls are the easy part. The durable part of agent governance is non-technical, and it decides whether the controls get used well.

Policy

What is allowed

Which data classifications agents may touch, which channels they may be published to, when a human must stay in the loop, and what an acceptable-use statement says for AI specifically rather than software generally.

Process

How work moves

How an agent gets reviewed, who approves publication, how it is promoted between environments, how it is retired, and what happens when it starts behaving differently from the day it shipped.

People

Who is accountable

Named owners for every agent above Zone 1, a coaching or champion function for makers, and a small group that reviews anything crossing a zone boundary. Ownerless agents are the most common governance debt.

4. Sharing and publishing are different problems

These get conflated constantly, and the controls for them live in different places.

 SharingPublishing
Question it answers Who is allowed to open, run or edit this agent? Where does this agent appear, and to which audience?
Typical levers Agent-level sharing (viewer or editor), security roles, environment access by security group, sharing limits in managed environments. Channels (Teams, a website, a custom app), the organizational catalog, deployment and assignment to users and groups.
Where administered Copilot Studio, Power Platform admin center, environment group rules. Microsoft 365 admin center (Integrated Apps), Copilot Studio channel configuration.
Zone 1 default Off. The agent stays with its maker. None beyond the maker's own experience.

The practical consequence: restricting sharing does nothing about an agent published to an unauthenticated public web channel, and blocking a channel does nothing about an agent quietly shared with two hundred colleagues as an editor. Both need setting.

5. The controls that implement the zones

Environment groups and rules

Environment groups are how a zone stops being a slide and becomes enforcement. You group environments, then apply rules to the group so every environment in it inherits the same posture. Rules available include sharing limits for agents with editor and viewer permissions, advanced connector policy, generative AI settings, external model access, access to conversation transcripts, release channel, backup retention, maker welcome content and a default deployment pipeline.

Environment routing

Routing is what prevents shadow AI. When a maker first opens Copilot Studio, Power Apps or Power Automate, routing creates or sends them to a personal developer environment inside the right group rather than dropping them in the default environment. Multi-rule routing extends this so different populations land in different groups. All routed environments are managed environments, which carries a premium licensing dependency worth confirming before you switch it on.

Data policies and connector control

Data policies (formerly DLP policies) classify connectors and block combinations that would move data across a boundary. Advanced connector policies, currently in preview, go further by restricting individual connector actions rather than whole connectors, which is what Zones 2 and 3 need when a connector is needed for reads but not for writes.

Identity the agent runs as

In Zone 1 an agent runs in the maker's context, which is the correct default: it can never see more than the person who built it. In Zones 2 and 3 that becomes a liability, because the agent inherits one person's access and breaks when they leave. Those zones should move to a service principal or managed identity scoped to least privilege, with the permissions documented as part of the review.

Sequencing tip: turn on routing before you tighten anything else. If you restrict the default environment first, makers who have nowhere else to go will find another tool entirely, and you will have traded visible risk for invisible risk.

6. Where you actually watch it

SurfaceWhat it answers
Power Platform inventory What exists across the tenant: agents, agentic apps, agent flows, environments and environment groups, with filtering, counts, column selection and export. Created, updated and deleted resources surface within about 15 minutes. Connector visibility, showing which connectors and operations each resource uses, is in preview.
Power Platform security posture Whether the tenant is configured safely, with preconfigured defaults and a security action center that lists outstanding tasks.
Copilot area in the admin center Agent usage and Copilot settings, including what Zone 1 makers are producing.
Microsoft 365 admin center What is available to users: Microsoft first-party agents, third-party agents and organization-created agents. Lifecycle actions live here — publish, deploy, assign, remove and block, per agent and per group.
Microsoft Purview The data-security and compliance layer across all of it: posture management for AI, data loss prevention, information protection, insider risk, communication compliance, eDiscovery, audit and oversharing assessment.
Agent counts will not match between surfaces, and that is expected. Each console answers a different question. Power Platform inventory shows what has been built in Power Platform. The Microsoft 365 admin center shows what is available to users, which includes first-party and third-party agents and agents authored outside Power Platform entirely. Reconciling the two numbers is a category error; read each for its own purpose.

Access to the inventory is role-scoped

Visibility into Power Platform inventory depends on Microsoft Entra role. Global administrator, Power Platform administrator, Dynamics 365 administrator and Global reader see everything. The AI administrator and AI reader roles see only AI-related resources: agents, agentic apps, agent flows, environments and environment groups — canvas apps, model-driven apps and cloud flows are out of scope for them. These are Entra roles, not the built-in Power Platform roles, and the latter are not supported for inventory access.

7. Standing it up

1

Name an owner and a small review group

Before any configuration. One accountable owner for agent governance, plus a handful of people who can review anything crossing into Zone 2 or 3. Without this, every later step becomes an unassigned ticket.

2

Write the policy in plain language

What data agents may use, what they may never do without a human, where they may be published, and who signs off. One page beats a framework nobody reads.

3

Turn on environment routing

Give every maker a personal developer environment inside a Zone 1 group. Confirm the managed-environment licensing implication first.

4

Create the environment groups and apply rules

One group per zone as a starting point. Set sharing limits, connector policy and generative AI settings at the group so new environments inherit posture automatically.

5

Set the promotion path out of Zone 1

Define what an agent must demonstrate to earn a managed environment, a shared audience and a named owner. Wire pipelines so promotion is a deployment, not a rebuild.

6

Connect Purview and set spending alerts

Data protection and cost are the two failure modes that show up after go-live rather than before. Both are cheaper to configure early than to retrofit.

7

Review the inventory on a schedule

Monthly is enough for most organizations. Look for ownerless agents, agents shared far beyond their zone, and anything in the default environment that should have been routed.

8. Common failure patterns

PatternWhat it causes
Governing by blockingMakers move to tools with no oversight at all. Risk does not reduce; it relocates and becomes invisible.
Personal building in the default environmentNo isolation, no clear ownership, and a shared space that slowly becomes production by accident.
One policy for all agentsEither Zone 1 is strangled to protect against Zone 3 risks, or Zone 3 inherits Zone 1 permissiveness. Both are common; the second is worse.
Agents running as a person indefinitelyAccess creep while they are there, and breakage when they leave. Move to a scoped service identity when the agent serves anyone but its maker.
Controlling sharing but not publishingAn agent locked down for editing but exposed on an unauthenticated channel.
No retirement pathInventory grows monotonically. Every unused agent is still a permission set and a support expectation.
