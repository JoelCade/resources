Agent Builder Governance

Sharing controls, at-scale cleanup of unused agents, cost visibility, and what actually happens to an agent’s environment and sharing settings when it gets copied into Copilot Studio. · September 2026

The one thing to remember: Agent Builder has two separate governance systems, not one. While an agent lives in Microsoft 365 Copilot, it is governed from the Microsoft 365 admin center (sharing rules, ownership, lifecycle rules, cost reporting). The moment someone selects Copy to Copilot Studio, the agent becomes a Copilot Studio agent stored in a Power Platform environment, and it switches to being governed from the Power Platform admin center instead — with a different sharing model, different environment rules, and no automatic carry-over of the settings it had before.

1. Two admin centers, two lifecycles

Before anything else, it helps to separate the two places an Agent Builder agent can live, because the controls are genuinely different in each one.

While in Agent Builder

Microsoft 365 admin center

Agents created directly in Microsoft 365 Copilot’s Agent Builder are managed under Copilot > Agents and Copilot > Settings > Data access > Agents. This covers sharing permissions, the agent registry, agent management rules, and Copilot-related cost/consumption views.

After Copy to Copilot Studio

Power Platform admin center

Once copied, the agent is a Copilot Studio agent stored in Dataverse inside a Power Platform environment. Governance moves to environment-level controls: Managed Environment sharing limits, data loss prevention (DLP) policies, connector policies, and Copilot Studio licensing/credit pages.

2. How agent sharing works, and how to make it granular

Sharing has two layers: what an individual owner can do when they share their own agent, and the org-wide policy an admin sets that constrains every owner in the tenant.

Per-agent sharing (owner-level)

Every Agent Builder agent has two access levels, set from its Share dialog:

RoleCan chatCan edit and manageNotes
Can edit (owner)YesYesFull rights to edit, share and manage. All owners are equal — any one of them can add/remove people or switch roles. Only individual users can be given this role, not security groups.
Can chat (viewer)YesNoCan interact with the agent but not modify it. Can be assigned to individuals or, via org-wide sharing, the whole tenant.

An owner can also flip an org-wide sharing for chat access toggle per agent, which publishes it into the internal Agent Store so anyone in the tenant can discover and chat with it. This toggle is what tenant-level sharing policy directly constrains.

Tenant-wide sharing policy (admin-level, the granular control)

This is the lever for controlling how far any agent in the tenant is allowed to be shared, set once and enforced for everyone. Go to Microsoft 365 admin center > Copilot > Settings > Data access > Agents > Sharing.

SettingEffect
All users (default)Every owner can share their agent with anyone in the organization, including turning on org-wide sharing.
Specific users or groupsOnly the named users or groups can share agents at all — the practical way to restrict who is allowed to spread agents beyond their own use, without banning agent creation itself.
No usersDisables org-wide sharing entirely. The org-wide sharing toggle appears grayed out in every agent’s Share dialog. Direct sharing with named individuals can still be used depending on tenant configuration.
This control is not retroactive. Changing the sharing policy only affects new sharing actions taken after the change. Agents that were already shared keep their existing access — you have to go back and manually update or revoke sharing on those agents individually.

Submitting to the org catalog is a separate, reviewed step

Sharing (chat access) and cataloging (discoverability in the Built by your org section of the Agent Store) are managed independently. An owner keeps full control of who an agent is shared with at any time, but making it broadly discoverable requires submitting it to the org catalog, where an admin reviews and approves the submission before it is published.

3. Removing unused agents and managing them at scale

Individually reviewing every agent does not scale once Agent Builder adoption grows. Two tools exist specifically for bulk cleanup, both in the Microsoft 365 admin center.

Agent management rules (bulk, conditions-based)

Under Copilot > Agents > Agent management rules, admins define conditions, preview the impacted agents, then apply a governance action across all of them in one action — instead of opening agents one at a time.

Block ownerless agents without usage

The direct answer to "clean up agents nobody is using." Targets agents that have lost their owner (the creator left the organization) and show no usage, and blocks them in bulk.

Reassign ownerless agents to manager

For agents an admin does not want to remove, this rule reassigns ownership automatically to the previous owner’s manager, based on Microsoft Entra ID hierarchy. Only supports agents created with Agent Builder.

Install Microsoft (1P) agents

Proactively installs Microsoft-published agents tenant-wide in one action, instead of relying on individual adoption.

Apply a template / reject stale publish requests

Applies a standard policy template to matching agents, or auto-rejects org-catalog publish requests that have sat unreviewed longer than a set number of days.

Per-agent actions in the agent registry

For one-off cleanup, the agent registry (Microsoft 365 admin center > Agents > All agents) gives every agent instance-level actions:

ActionEffect
BlockAgent stays in the registry but becomes inactive tenant-wide; the creator is notified; reversible at any time.
ReassignTransfers ownership to a different user; the new owner gets full control and editing rights, the old owner loses access.
DeleteRemoves the agent, its Entra ID identity, and its configuration entirely. Historical telemetry is retained for compliance. Agent Builder agents can be deleted by their owner through the registry; agents built directly in Copilot Studio require Power Platform environment admin permissions to delete.

All governance actions taken from the registry — block, reassign, delete — are logged in Microsoft Purview, so bulk cleanup remains auditable.

4. Cost controls and reporting as agents spread across the org

Agent Builder agents themselves don’t consume Dataverse storage entitlement, but any agent that uses AI capabilities consumes Copilot Credits, and the more an agent is shared, the more it gets used, and the more it costs. Cost visibility and controls live in the Power Platform admin center > Licensing > Copilot Studio pages, which apply to agent usage broadly (Agent Builder, Copilot Studio, and other agent-consuming workloads alike).

Reporting: four views of the same consumption

ViewWhat it shows
TenantPurchased, allocated, and consumed Copilot Credit capacity across the whole organization.
EnvironmentPrepaid versus pay-as-you-go consumption per environment, and which environments are in overage.
AgentMonth-to-date billed credits, configured consumption limits, and status, for each individual agent.
ReportDownloadable, detailed consumption data for further analysis.
Costs are not attributed to individual makers or end users. Copilot Studio and Agent Builder usage is billed at the environment and agent level only. If a heavily shared agent is driving unexpected cost, that shows up as agent-level or environment-level consumption, not a per-person breakdown — permissions and per-agent limits are the levers, not user-level billing.

Stopping runaway spend, not just watching it

  • Per-agent consumption limits. In Licensing > Copilot Studio > Manage Agents, set a monthly credit cap on an individual agent so it cannot exceed a defined amount before enforcement kicks in.
  • Pay-as-you-go billing policies. Link an environment to an Azure subscription to bill overage through Azure meters, then use Azure Cost Management to set budgets and alerts on the associated Power Platform account resource.
  • Budgets and alerts warn; they do not stop usage. An Azure budget alert is a notification, not a circuit breaker. To create an actual stopping point, also configure the agent-level Stop usage limit, and assign an accountable business owner to each pay-as-you-go billing plan and environment.
  • Overage enforcement without pay-as-you-go. If an environment runs out of prepaid capacity and has no pay-as-you-go link, agent flow actions get blocked until capacity is reallocated from elsewhere in the tenant, more credits are purchased, or pay-as-you-go is enabled.

5. What happens when an agent is copied to Copilot Studio

The Copy to Copilot Studio feature unlocks lifecycle management, analytics and enterprise governance beyond what Agent Builder offers on its own — but it is a real migration, not a link. The agent gets a new home, and that home determines which rules now apply.

Which environment does it land in?

1

You choose the environment; it is not automatic

The person copying the agent is prompted to pick the destination environment. The environment must have a Dataverse data store, sit in a supported data location, and the user must hold the right security role in it. There is no hidden default — whatever environment is picked in that dialog is where the agent is stored.

2

Environment routing changes what gets preselected

If an admin has turned on Environment routing in the Power Platform admin center, makers are automatically directed into their own personal developer environment instead of the tenant’s shared default environment, and that routed environment is preselected in the copy dialog. Personal developer environments are private, per-maker sandboxes, similar in spirit to an individual OneDrive — they exist so experimentation doesn’t collide with other makers’ work or with production content sitting in the default environment.

3

Without routing turned on, agents default to the default environment

If environment routing is off (it is off by default and must be explicitly enabled), or no routing rule matches the maker, the copy lands in the tenant’s shared default environment — the same environment most low-code assets end up in when nobody has set up a dedicated environment strategy.

Personal developer environments are not permanent by default. They can be subject to automatic cleanup after a period of inactivity. If a maker stops signing in, the environment — and the copied agent living in it — can be turned off. Admins and users should periodically sign in to retain access, and admins can review the automatic cleanup policy to decide whether recovery is possible.

Do sharing controls carry over? No — the agent inherits new rules from the destination environment

This is the part that catches people out: the Microsoft 365 admin center sharing policy that governed the agent in Agent Builder does not travel with it into Copilot Studio. Microsoft is explicit that the sharing limit control in the Microsoft 365 admin center is a different system from the sharing limit control in the Power Platform admin center. Once the copy completes, the agent is subject to whatever the destination environment has configured, not what the original agent had:

  • Managed Environment sharing limits — if the destination is a Managed Environment, admins can allow or block sharing with editors, allow or block sharing with viewers (individuals or security groups), restrict sharing to individuals only, and cap the number of viewers an agent can be shared with. These are configured per environment or applied at scale via environment groups.
  • Data loss prevention (DLP) policies on the environment, which govern which connectors and data sources the copied agent can use.
  • Advanced connector policies, which govern high-privilege connectors specifically.

Practically: if you want a copied agent to inherit tight sharing discipline, that discipline has to already exist as policy on the environment you pick (or route makers into) — it is not something the Agent Builder agent brings with it.

Ownership and identity also change hands

Admin management of the agent moves entirely from the Microsoft 365 admin center to the Power Platform admin center once copied. The agent is stored in Dataverse and managed as part of a Power Platform solution, so ALM practices (versioning, staged deployment, security roles on the environment) apply to it going forward, and the original Agent Builder registry entry and the Copilot Studio copy are managed as two separate lifecycles from that point on.
