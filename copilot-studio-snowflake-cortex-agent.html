Microsoft Copilot Studio · Snowflake Cortex

Connecting Copilot Studio to Snowflake Cortex Agents

How to let a Copilot Studio agent answer questions from Snowflake data by calling a Cortex Agent through the Snowflake connector, configured as a tool rather than a scripted topic. Covers the Entra External OAuth setup, the stored procedure bridge, and the production hardening the quickstart leaves out. · August 2026

The one thing to remember: Snowflake Cortex Agents are not called directly by Copilot Studio. You wrap the Cortex Agent in a Snowflake stored procedure, then expose that procedure to your Copilot Studio agent as a tool that runs a single SQL statement. The hard part is not the wiring, it is the Microsoft Entra External OAuth trust between the two platforms.

What this pattern gives you

Snowflake Cortex Agents orchestrate across structured and unstructured data. Cortex Analyst handles text-to-SQL over a semantic model, and Cortex Search handles retrieval over unstructured content. A Cortex Agent plans which of those tools to use, executes them, and returns a written answer.

Rather than rebuilding that reasoning inside Copilot Studio, you let Snowflake do the data reasoning and let Copilot Studio be the conversational surface your users already work in. The agent keeps all of its other capabilities, including Microsoft 365 knowledge, other tools, and other connected agents, and simply gains one more tool that happens to be very good at answering questions about your Snowflake estate.

User Asks a question in Teams or the agent's chat surface
→
Copilot Studio agent Generative orchestration decides the Snowflake tool is the right one
→
Snowflake connector Runs one SQL statement: a CALL to the stored procedure
→
Stored procedure Posts the question to the Cortex Agent REST endpoint
→
Cortex Agent Orchestrates Analyst and Search, returns an answer

Why a tool and not a topic

Snowflake's quickstart demonstrates this using a Copilot Studio topic with a trigger phrase such as "use cortex agent", followed by a question node. That works, but it forces the user to learn a magic phrase and then answer a second prompt before anything happens. It also sits outside the agent's own reasoning.

Configuring the same connector call as a tool is the better pattern. The agent reads the tool's description, decides on its own when a question belongs to Snowflake, passes the user's question straight through, and folds the result into its answer. No trigger phrase, no extra turn, and the tool composes naturally with everything else the agent can do. Snowflake's own guide notes that tools work with a similar flow.

 Topic with trigger phraseTool (recommended)
How it firesUser types a specific phraseAgent decides from the tool description

What you need before you start

Microsoft side
  • Copilot Studio with an agent using generative orchestration
  • Premium connector entitlement, because the Snowflake connector is premium
  • Permission to register applications in Microsoft Entra ID, or an identity admin who can
  • A Power Platform environment where the connector is permitted by your data policies
Snowflake side
  • An account with Cortex features available in your region
  • A Cortex Analyst semantic model, a Cortex Search service, or both
  • A Cortex Agent that uses them as tools
  • Rights to create a security integration, a role, a user, and a stored procedure
Region and cloud availability. The Snowflake connector is not available in US Government (GCC, GCC High), Department of Defense, or China operated by 21Vianet regions. Cortex feature availability also varies by Snowflake region. Confirm both before you commit to this design.

Step 1 — Build the Cortex Agent in Snowflake

This part is entirely Snowflake-side work and should be finished and tested before Microsoft enters the picture. In outline:

  • Create a Cortex Search service over your unstructured content, such as call transcripts, tickets, or documents.
  • Create a Cortex Analyst semantic model over the structured tables you want queried in natural language.
  • Create a Cortex Agent that lists both as tools, and give it orchestration and response instructions.

Response instructions matter more than people expect here. The answer is going to be rendered in a chat window, so instruct the agent to return concise text without visualizations. Snowflake's sample instructions ask for responses that are "concise and direct" and "suitable for all chat interfaces with no visualizations".

Test the agent inside Snowflake first. If it does not give good answers in Snowsight, it will not give good answers in Copilot Studio, and you will waste time debugging the wrong layer.

Step 2 — Configure Entra External OAuth

This is the step that takes real effort and needs both an Entra administrator and a Snowflake administrator. You are establishing a trust so that a token issued by Microsoft Entra ID is accepted by Snowflake as proof of identity.

You create two Entra app registrations. The first is the OAuth resource, which represents Snowflake itself and carries the Application ID URI and the role definitions. The second is the OAuth client, which represents the caller and holds the client ID and secret that the connector uses.

1

Create the OAuth resource application

Single tenant. Set an Application ID URI in the form api://<application-id>. Then define how the Snowflake role travels in the token:

  • Service principal auth: add an app role in the manifest whose value is session:role:<role>, for example session:role:analyst.
  • Delegated auth: expose a scope named session:scope:<role>.
2

Create the OAuth client application

Also single tenant. Generate a client secret and record it, then grant this client permission against the resource application created in step 1 and grant admin consent. For delegated authentication you also add the redirect URI:

https://global.consent.azure-apim.net/redirect/snowflakev2

If that redirect URI is missing, the connection will simply fail to complete.

3

Collect the values Snowflake needs

From the resource application's endpoints, gather the issuer (the entityID from the federation metadata, in the form https://sts.windows.net/<tenant-id>/) and the signing key URL (the jwks_uri from the OpenID Connect metadata, in the form https://login.microsoftonline.com/<tenant-id>/discovery/v2.0/keys).

4

Validate the token before touching Snowflake

Request a token and inspect it. For service principal authentication, the sub claim in that token becomes the login name of the Snowflake user you are about to create. Confirming this now saves a great deal of guesswork later.

curl -X POST \
  -H "Content-Type: application/x-www-form-urlencoded;charset=UTF-8" \
  --data-urlencode "client_id=<OAUTH_CLIENT_ID>" \
  --data-urlencode "client_secret=<OAUTH_CLIENT_SECRET>" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "scope=api://<APPLICATION_ID>/.default" \
  'https://login.microsoftonline.com/<TENANT_ID>/oauth2/v2.0/token'
5

Create the Snowflake security integration

The external_oauth_audience_list value must match the Application ID URI exactly. Note the claim mapping differs between the two authentication modes: service principal maps on sub, delegated maps on upn.

CREATE SECURITY INTEGRATION external_oauth_azure
  TYPE = external_oauth
  ENABLED = TRUE
  EXTERNAL_OAUTH_TYPE = azure
  EXTERNAL_OAUTH_ISSUER = '<AZURE_AD_ISSUER>'
  EXTERNAL_OAUTH_JWS_KEYS_URL = '<AZURE_AD_JWS_KEY_ENDPOINT>'
  EXTERNAL_OAUTH_AUDIENCE_LIST = ('<APPLICATION_ID_URI>')
  EXTERNAL_OAUTH_TOKEN_USER_MAPPING_CLAIM = 'sub'
  EXTERNAL_OAUTH_SNOWFLAKE_USER_MAPPING_ATTRIBUTE = 'login_name';

Then create the Snowflake user whose LOGIN_NAME matches the claim you mapped, and grant it a purpose-built role.

CREATE OR REPLACE USER AAD_SP_USER
  LOGIN_NAME = '<sub value from the decoded token>'
  DISPLAY_NAME = 'Entra service principal user'
  COMMENT = 'Used by the Power Platform Snowflake connector';

CREATE ROLE IF NOT EXISTS ANALYST;
GRANT ROLE ANALYST TO USER AAD_SP_USER;

Verify the trust end to end before moving on:

SELECT SYSTEM$VERIFY_EXTERNAL_OAUTH_TOKEN('<token>');

Three things that commonly break this step

  • The blocked role list. Snowflake places privileged roles on a blocked list for external OAuth by default. Describe the integration and confirm the role you intend to use is not blocked. Snowflake's quickstart disables this protection wholesale with ALTER ACCOUNT SET EXTERNAL_OAUTH_ADD_PRIVILEGED_ROLES_TO_BLOCKED_LIST = FALSE. That is a convenience for a sandbox. Prefer leaving the protection on and using a non-privileged role.
  • An existing integration for another Microsoft service. If a security integration already exists for something such as Power BI, do not create a competing one blindly. Alter the existing integration to add the new audience, or set requestedAccessTokenVersion to 2 in the application manifest so the tokens carry a distinct issuer and a separate integration is viable.
  • Case sensitivity. Warehouse, role, database, and schema values must be supplied in the same letter case as they exist in Snowflake.

Step 3 — Wrap the Cortex Agent in a stored procedure

The connector executes SQL. Cortex Agents are invoked over a REST endpoint. The stored procedure is the bridge between those two facts: it accepts a question as a string, posts it to the agent's :run endpoint using Snowflake's internal request helper, parses the streamed response, and returns plain text.

First grant the role what it needs. Cortex access is granted through Snowflake database roles:

GRANT USAGE ON DATABASE SALES_INTELLIGENCE TO ROLE ANALYST;
GRANT USAGE ON SCHEMA SALES_INTELLIGENCE.DATA TO ROLE ANALYST;
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_AGENT_USER TO ROLE ANALYST;
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_ANALYST_USER TO ROLE ANALYST;
GRANT USAGE ON CORTEX SEARCH SERVICE SALES_CONVERSATION_SEARCH TO ROLE ANALYST;
GRANT SELECT ON TABLE SALES_INTELLIGENCE.DATA.SALES_METRICS TO ROLE ANALYST;
GRANT USAGE ON WAREHOUSE SALES_INTELLIGENCE_WH TO ROLE ANALYST;
Do not copy the quickstart's GRANT ROLE ACCOUNTADMIN TO ROLE ANALYST into production. Snowflake's published sample includes that line to keep a demo moving. It hands full account administration to the identity your Copilot Studio agent authenticates as. Grant only the specific privileges listed above, and nothing more.

Then create the procedure. The shape below follows Snowflake's published example:

CREATE OR REPLACE PROCEDURE call_cortex_agent_proc(query STRING)
RETURNS STRING
LANGUAGE PYTHON
RUNTIME_VERSION = '3.9'
PACKAGES = ('snowflake-snowpark-python')
HANDLER = 'call_agent'
EXECUTE AS CALLER
AS $$
import json
import _snowflake

def call_agent(query: str):
    API_ENDPOINT = "/api/v2/databases/SALES_INTELLIGENCE/schemas/DATA/agents/SALES_INTELLIGENCE_AGENT:run"
    API_TIMEOUT = 15000  # milliseconds

    payload = {
        "messages": [
            {"role": "user", "content": [{"type": "text", "text": query}]}
        ]
    }

    try:
        resp = _snowflake.send_snow_api_request(
            "POST", API_ENDPOINT, {}, {}, payload, None, API_TIMEOUT
        )

        if resp["status"] != 200:
            return f"Error: {resp['status']}"

        response_content = json.loads(resp["content"])

        collected = []
        for event in response_content:
            if event.get("event") == "response.text":
                collected.append(event.get("data", {}).get("text", ""))
            elif event.get("event") == "response.text.delta":
                collected.append(
                    event.get("data", {}).get("delta", {}).get("text", "")
                )

        answer = "".join(collected).strip()
        return answer if answer else "No response within the time limit."

    except Exception as e:
        return f"Timeout or error: {str(e)}"
$$;
One deliberate change from the published sample. Snowflake's version returns on the first text chunk it sees, which is a latency trick that can truncate the answer mid-sentence. The version above accumulates the full response before returning. If you need speed more than completeness, revert it, but do so knowingly.

Test the procedure in a worksheet before going near Copilot Studio:

CALL sales_intelligence.data.call_cortex_agent_proc('What is the SecureBank deal worth?');

Step 4 — Add the connector as a tool in Copilot Studio

In your agent, go to Tools, add a new tool, and choose the Snowflake connector's Submit SQL Statement for Execution action. When prompted, create the connection using the values from your Entra configuration.

Connection fieldValue
TenantYour Entra tenant ID
Client IDThe OAuth client application's ID
Client SecretThe secret generated on that client application
Resource URLThe Snowflake OAuth audience, matching the Application ID URI
Snowflake SaaS URLYour account URL without the https prefix
Database, Warehouse, Role, SchemaMatching the case used in Snowflake exactly

Then configure the tool itself. Three settings do most of the work:

The statement

The action's statement input carries the SQL. You want the agent to supply the question, so the statement becomes a call to your procedure with the question inserted:

CALL sales_intelligence.data.call_cortex_agent_proc('<the user question>');

Mark that inserted portion as an input the agent fills in at run time, rather than a fixed value. Keep the surrounding single quotes.

The tool description

This is the single most important field on the page, because generative orchestration uses it to decide whether to call the tool at all. Describe the data, not the plumbing. "Answers questions about sales pipeline, deal values, win rates, and the content of recorded sales calls" will route correctly. "Calls a Snowflake stored procedure" will not, because no user ever phrases a question that way.

The input description

Describe the input as the user's full question in natural language. This tells the orchestrator to pass the question through intact rather than reducing it to a keyword, which matters because the Cortex Agent is itself expecting natural language.

Watch the timeout. A Cortex Agent that plans, runs a generated SQL query, and writes an answer can take longer than a simple connector call. The stored procedure has its own timeout, and the connector action has a separate one. Both must be generous enough for a real answer, and both should be shorter than the patience of the person waiting. Tightening the agent's response instructions is usually a better fix than raising timeouts indefinitely.

Security considerations worth designing for

The statement is assembled as text

The connector action takes a SQL statement as a string, and there is no documented parameter binding. That means the user's question is being placed inside a quoted SQL literal. A question containing an apostrophe will break the statement, and a deliberately crafted input is a SQL injection consideration rather than a theoretical one.

Mitigate it in layers. Escape or strip single quotes before the value reaches the statement. Keep the Snowflake role minimal so that even a successful injection reaches almost nothing. Consider having the procedure validate its own input length and reject anything implausible. Do not rely on the model to sanitize on your behalf.

Service principal means a shared identity

With service principal authentication, every question reaches Snowflake as the same user, regardless of who asked it. Snowflake's row-level security and role-based access therefore apply to that shared identity, not to the individual. If different users are supposed to see different rows, service principal authentication alone will not deliver that, and you should evaluate delegated authentication so that each user's own identity flows through.

Governance follows the connector

This is an ordinary Power Platform connection, so tenant data loss prevention policies apply to it. Classify the connector deliberately before a pilot spreads, rather than discovering the policy conflict at rollout.

A sensible order of work

  1. Confirm region availability, premium licensing, and how the connector is classified in your data policies.
  2. Build and test the Cortex Agent in Snowflake until the answers are genuinely good.
  3. Book one working session with an Entra administrator and a Snowflake administrator and complete the OAuth trust end to end, verifying the token before you leave the session.
  4. Create the least-privilege role and the stored procedure, and test the procedure from a worksheet.
  5. Add the tool in Copilot Studio, then spend real time on the tool and input descriptions.
  6. Test with questions phrased the way your users actually phrase them, not the way the documentation phrases them.
  7. Harden before rollout: input handling, timeouts, role scope, and a decision on shared versus delegated identity.
Worth evaluating alongside this. If your organization's data strategy is consolidating on a governed semantic layer, compare this pattern against mirroring Snowflake into OneLake and using a Fabric data agent. Both surface the same data in Copilot Studio. The right answer depends on where you want the semantic model to live and who you want maintaining it.
