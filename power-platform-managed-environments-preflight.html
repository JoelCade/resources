Managed Environments: Pre-Deployment Inventory and Checklist

Work out who is in the environment, who is actually licensed, and what it will cost — before you turn Managed Environments on. Includes a downloadable PowerShell inventory script · August 2026.

The one thing to remember: enabling Managed Environments does not lock unlicensed users out. Enforcement is notification-based and escalates over roughly two weeks. That gives you runway — but the licensing obligation is real from the moment you switch it on, so do the inventory first rather than discovering the gap through in-app warnings.

This page is the operational companion to Power Platform Licensing & Managed Environments. That page explains the concepts: seeded versus premium, the licensing paths, and what Managed Environments actually unlocks. Start there if the model is new to you. This page assumes you have decided to proceed and need to work out who needs a license before you flip the switch.

1. Why you need a pre-flight inventory

There is a purpose-built report in the Power Platform admin center called Users requiring licenses in Managed Environments. It is genuinely useful, and it is the right tool for ongoing compliance monitoring. It is the wrong tool for planning, for two reasons:

  • It only reports on environments that are already flagged as managed. Before you enable, there is nothing to report on.
  • It only lists users who launched an app in the selected month. Anyone who has access but has not opened anything recently is invisible.

So a genuine pre-enablement inventory has to be composed from three sources and joined manually. That is what the script further down does.

A lower-effort alternative worth considering. Because enforcement is notification-based rather than a hard block, you can enable Managed Environments on a single low-risk pilot environment, let the native report populate for a month, and get Microsoft's own verdict instead of reverse-engineering it. That is less work and higher fidelity. Do not do this on a business-critical environment with a nervous user base, and be aware users in the pilot will start seeing notifications.

3. The Dynamics 365 Pro trap

This one is worth calling out on its own, because the Microsoft Learn article reads as ambiguous. The Learn page names only Premium, Enterprise, and Team Members as qualifying, yet a separate clause refers to Power Apps rights included with Pro licenses being valid within the context of the licensed application. Read alone, that looks like a partial grant.

The Licensing Guide settles it. Page 9, footnote 2:

“Dynamics 365 Pro does not have use rights for Power Apps or Power Pages.”

And page 24, footnote 1 removes any remaining doubt about what “standalone” means for this entitlement:

“Standalone licenses refers to full Power Apps, Power Automate, Power Pages and Copilot Studio licenses and does not include the limited Power Apps, Power Automate and Power Pages use rights that come with select Dynamics 365 and Microsoft 365 licenses.”

So Sales Professional and Customer Service Professional users in a managed environment need a per-app plan, a pay-as-you-go meter, or an upgrade. Plan for it.

A naming trap that produces false negatives

Some Professional SKU part numbers embed the word ENTERPRISE. For example, DYN365_ENTERPRISE_SALES_PROFESSIONAL is a Professional license despite the name. Any script that pattern-matches on ENTERPRISE first will classify these as covered, which is a false negative on exactly the population you most need to find. The script below handles this by evaluating Professional patterns before Enterprise patterns.

4. The four-step inventory

1

Define the population

The licensing question is about active users in that environment, not tenant-wide seats. Query the Dataverse systemuser table and filter to access mode Read-Write, which is the license-consuming population. Exclude non-interactive, administrative, and application users, and exclude disabled accounts unless you are also running an access review.

2

Pull actual license assignments from Entra ID

The admin center gives you aggregate counts. You need per-user SKUs, which means Microsoft Graph. Critically, expand group-based licensing. A large share of miscounts come from licenses assigned through a group that the admin forgot to enumerate. Graph exposes this on licenseAssignmentStates via the assignedByGroup field.

3

Join and classify into buckets

Every user should land in exactly one bucket, and unknown SKUs should be surfaced rather than assumed. An inventory that quietly guesses is worse than one that admits what it does not know.

4

Corroborate against real usage before buying

Do not size the purchase from the user list. Size it from actual app launches. Go to Licensing > Power Apps > Download Reports > Active users for last-launch details. Users who appear in your environment population but never launch anything may need removing rather than licensing.

5. The inventory script

Get-ManagedEnvLicenseInventory.ps1

A read-only PowerShell script that performs steps 1 to 3 automatically and writes an Excel workbook (or CSVs) with a per-user verdict. It changes nothing in Dataverse or Entra ID.

Download the script Read the documentation

Requirements

  • PowerShell 5.1 or PowerShell 7 and above
  • Azure CLI on the PATH, signed in with az login
  • A Dataverse account that can read the systemuser table in the target environment
  • Directory read access in Entra ID. If Graph returns 403, use an account with Directory.Read.All, User.Read.All, or Organization.Read.All.
  • Optional: Install-Module ImportExcel -Scope CurrentUser for a single workbook instead of CSVs

6. Limits you must account for

This is entitlement, not usage. A user can be unlicensed and never launch an app, in which case the right answer may be to remove them rather than buy them a license. Always cross-check against the Active users report before purchasing.
Per-app plans and pay-as-you-go meters are invisible to any per-user report. Both are allocated at the environment level, not to a user, so they cannot appear in Entra data. If you use either, treat the non-qualifying count as an upper bound and reconcile against Licensing > Power Apps > Environments.
Unknown SKUs are surfaced, never assumed. Anything unrecognized is reported as Unclassified and listed at the end of the run so the rules can be extended. New SKUs appear regularly, so expect to add a few.

7. Pre-deployment checklist

Work top to bottom. The first four are the inventory itself; the rest are the operational readiness items that tend to get skipped.

Inventory

  • Confirm which environment is being managed. For a Dynamics 365 finance and operations deployment this is the linked Dataverse environment, not the finance and operations environment itself.
  • Enumerate the license-consuming population in that environment (Read-Write access mode, enabled, non-application users).
  • Pull per-user license assignments from Entra ID, including group-assigned licenses.
  • Classify every user, and resolve anything that lands as Unclassified.

Reconciliation

  • Check environment-level per-app allocations and pay-as-you-go meters in the admin center, and subtract those users from the gap.
  • Cross-check the gap list against the Active users report. Separate “needs a license” from “should be removed”.
  • Identify any Dynamics 365 Pro / Professional users specifically, since these are the most commonly misclassified population.
  • Confirm no one is relying on the Developer Plan to run assets in this environment.

Commercial

  • Decide the remediation path per user group: per-app plan, pay-as-you-go meter, standalone premium license, or Dynamics 365 upgrade.
  • Confirm sufficient license capacity exists in the tenant before enabling.
  • Consider enabling auto-claim policies so active users are licensed automatically rather than by hand.
  • Validate the final position against your agreement and the current Licensing Guide. Pricing and SKU rules change.

Operational readiness

  • Decide whether to pilot on a low-risk environment first.
  • Brief the service desk. Users will see in-app notifications, and the desk should know what they mean.
  • Check whether default environment routing is in scope. It creates managed developer environments automatically, which brings this same licensing rule with it.
  • Schedule a re-run of the inventory 30 days after enabling, and compare against the native compliance report.

8. What enforcement looks like

Notifications escalate rather than blocking immediately. Users keep working throughout.

StageWhat the user seesTiming
Informational“This app requires a valid Power Apps license. Request a license from your admin.”On first affected launch
WarningSame message, escalated presentation.After 7 days without a license
Error“Action required — this app requires a valid Power Apps license… for continued access.”After a further 7 days, and persists

Users can request a license directly from the notification. Requests surface in the Power Platform admin center under Actions > Recommendations, and in the Microsoft 365 admin center under Billing > Licenses > Requests.
