Agent Access and Catalog Strategy for Microsoft 365

How to make in-house agents discoverable without turning agent access into a shadow IT problem. · September 2026

The one thing to remember: use Agent Store as the employee-facing catalog and Microsoft 365 admin center as the approval and lifecycle control plane. Build a separate catalog only when you need to represent agents that cannot be surfaced in Copilot.

The short answer

Yes. Microsoft provides an out-of-the-box catalog experience for agents: Agent Store in Microsoft Copilot. It is the central place where users discover and install agents from Microsoft, trusted partners, and your own organization.

For organization-built agents, the usual path is: a maker or developer builds the agent, submits it for admin review, an admin approves it in Microsoft 365 admin center, and the agent appears in Agent Store under the organization-owned collection.

QuestionRecommended answer
Where should users find approved agents?Agent Store in Microsoft Copilot, with Teams app store exposure where Teams is a target channel.
Where should admins manage the lifecycle?Microsoft 365 admin center, especially the Agents area, Agent Registry, Requests, and Copilot controls.
How should makers distribute broadly?Publish to the Microsoft Copilot and Microsoft Teams channel from Copilot Studio, then wait for admin approval.
How should custom or external agents be included?Package them with Microsoft 365 Agents Toolkit or integrate with Agent 365 SDK, then submit them for admin approval.
Should every prototype go into the catalog?No. Use private sharing or a pilot group first, then promote only owned, reviewed, supported agents.

Recommended access model

1. One front door

Make Agent Store the default user experience for approved in-house agents. Avoid publishing one-off links as the primary access model; they are hard to govern, hard to retire, and easy to lose.

2. Group-based deployment

Deploy agents to security groups that map to business roles, pilot cohorts, or departments. Keep "entire organization" for agents with broad utility and low data/action risk.

3. Approval before scale

Require admin review before an agent reaches the organizational catalog. Review the agent's owner, purpose, data sources, knowledge, tools, actions, and supported host products.

4. Lifecycle ownership

Every published agent should have an owner, support contact, review date, intended audience, and retirement path. A catalog without lifecycle management becomes a cupboard full of enthusiastic experiments.

How the catalog flow works

1

Build and test the agent.

Use Copilot Studio for most business agents. Use Agent Builder or SharePoint agents for lighter knowledge scenarios. Use Azure AI Foundry, custom code, Microsoft 365 Agents Toolkit, or Agent 365 SDK when you need a pro-code implementation or an agent built outside Copilot Studio.

2

Submit for review.

For Copilot Studio, select the Microsoft Copilot and Microsoft Teams channel, confirm the agent should be available in Microsoft Copilot, fill in the catalog details, and save or publish the request for admin review.

3

Review in Microsoft 365 admin center.

Admins go to Agents → All agents → Requests, open the pending agent, and review capabilities, data access, maker or developer details, risks, and intended availability.

4

Publish, reject, block, or deploy.

Approved agents can be published to Agent Store and assigned to the whole organization, specific users, or groups. Admins can also block, remove, or restrict agents that are not appropriate for the tenant.

Recommended rollout pattern

  1. Define catalog rules. State what qualifies for publication, what must stay shared or pilot-only, and who can approve.
  2. Create maker guidance. Require clear name, description, owner, intended audience, data sources, actions, support model, and review date.
  3. Use rings. Start with maker test access, then pilot group, then department or role-based deployment, then organization-wide deployment only when justified.
  4. Separate install from assignment. Some agents should be visible for users to install. Others should be deployed directly to a group because they are part of a managed process.
  5. Review data and actions. Treat custom actions, connectors, APIs, and write operations as the highest-risk part of an agent, not the greeting text.
  6. Monitor and retire. Review usage, owner health, data dependencies, and stale agents quarterly.
Boundary to remember: not every agent type has the same publishing path. For example, Microsoft documentation notes that declarative agents built with SharePoint cannot be published to an organizational catalog, so they are better treated as team-local knowledge assets rather than enterprise catalog entries.

Decision guide

If the agent is...Use this access strategy
A broadly useful HR, IT, finance, sales, or operations assistantPublish to Agent Store after admin review and assign by group or organization.
A departmental agent with limited scopePublish to Agent Store but assign only to the relevant security group.
A prototype or work-in-progressUse private sharing or a pilot cohort. Do not add it to the organization catalog yet.
A SharePoint-created knowledge agentShare with the team where it belongs. Do not design your enterprise catalog strategy around this path.
A custom-code, Foundry, or third-party platform agentPackage or integrate it with the Microsoft 365 Agents Toolkit or Agent 365 SDK, then submit for admin approval.
A regulated or action-heavy agentUse explicit assignment, stronger review, owner attestation, and a shorter recertification cycle.

Minimum publication checklist

Owner Audience Data sources Actions Security review Support path Review date
  • Named business owner and technical owner.
  • Plain-language description of what the agent does and what it should not do.
  • Defined audience and assignment group.
  • Documented knowledge sources, connectors, APIs, and write actions.
  • Confirmation that data access follows least privilege.
  • Support contact, feedback route, and retirement plan.
  • Quarterly or semiannual review date, with shorter cycles for high-risk agents.
