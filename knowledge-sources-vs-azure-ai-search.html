When Built-In Knowledge Sources Are Not Enough

Why grounded agents answer inconsistently, how to tell a configuration problem from an architecture problem, and the signals that mean it is time to move to a purpose-built Azure AI Search index. · August 2026

The one thing to remember: when an agent answers well sometimes and poorly other times, the model is almost never the problem. Retrieval is the problem. Built-in knowledge sources are optimized for fast setup, which means they make the retrieval decisions for you and expose almost no dials. That is the right trade for most agents. It stops being the right trade at a predictable point, and the skill is recognizing that point rather than reaching it by accident.

1. What actually happens when an agent answers from knowledge

A grounded answer is not one operation. It is a short pipeline, and a failure anywhere in it produces the same symptom for the user: a vague answer, a wrong answer, or "I could not find anything."

1

Ingest

Content is read from the source and prepared. Depending on the source type, this means either copying and indexing the content, or relying on an existing search index that a different system maintains. Content that cannot be read at this stage is silently absent for everything that follows.

2

Chunk

Documents are split into passages. Chunk boundaries decide what facts can appear together in a single retrievable unit. A definition separated from its exception by a chunk boundary can no longer be retrieved as one idea.

3

Retrieve and rank

The user's question is turned into a query, candidate passages come back, and a small number of the highest-ranked passages are selected. This is the single most influential step, and it is the one built-in sources hide most completely.

4

Trim by permission

Results the asking user is not entitled to see are removed. This happens live against the source system, so two people asking the same question can legitimately get different answers, and one of them can get nothing.

5

Generate, cite, and moderate

The model composes an answer from the surviving passages and attaches citations. Content moderation can suppress the result, and in configurations that require grounding, an answer without a citation may be withheld even when it was correct.

Every one of those stages can fail quietly. That is why "unreliable" is the usual description rather than "broken."

2. The silent failure modes

Before concluding that the platform cannot do the job, rule out the failures that produce no error message. These are the ones that consume the most troubleshooting time precisely because nothing looks wrong.

FailureWhat you seeHow to confirm it
Content exceeds a processing size limit The item shows as connected and can even appear in search results, but its contents are never used in an answer Check the size distribution of your content against the documented limit for the source type and licensing you have
Protection blocks indexing The item shows as Ready and never answers Look for sensitivity labels at Confidential or above, and for password protection
Indexing has not completed Recently added content returns nothing Status cycles through In Progress before returning to Ready; scheduled refresh cycles are measured in hours and cannot be forced
Permission trimming Works for the maker, returns nothing for some users, no error Test with a least-privileged account, and verify authentication scopes and consent
Content moderation filtered the response No answer, no explanation Only visible through application telemetry; it is invisible in the chat itself
Citation missing, so the answer is withheld Intermittent. The same question answers on one attempt and not the next Happens when grounded-only behavior is enforced and the model omits an in-text citation
Unsupported question shape Consistent failure on a specific kind of question, while other questions work Questions that name a file, count items, list folder contents, or filter on metadata are not what document retrieval does
Instrument first. Connect the agent to application telemetry before you spend a week guessing. Moderation events, retrieval behavior, and filtered responses are not observable from the chat window. Without telemetry you are troubleshooting a pipeline you cannot see.

3. Triage before you re-architect

Moving to a custom retrieval stack is a real project. Work through this first, because a meaningful share of "the knowledge source does not work" reports resolve here.

  1. Confirm the content is actually eligible. Size, file type, protection status, and indexing state. Eligibility is binary and silent.
  2. Confirm the source system can find it. Search for the content directly in the underlying system using the same words the user used. If the source cannot find it, the agent will not either.
  3. Check which ingestion path you chose. Several platforms offer more than one way to connect the same repository, and they behave very differently in freshness, search quality, storage consumption, and citation granularity. Picking the wrong one is common and easily reversed.
  4. Separate question types. Sort failing questions into "should work" and "was never supported." Retrieval answers questions about content, not questions about the file system around the content.
  5. Scope the agent narrowly. One agent pointed at everything performs worse than several agents pointed at coherent bodies of content. Narrow scope improves ranking more reliably than prompt engineering does.
  6. Tune instructions for citation behavior. Ask explicitly for in-text citations, and remove instructions that impose rigid output formats, which can suppress the citation markers grounding depends on.
  7. Check licensing-dependent behavior. Some retrieval quality and size ceilings change based on what is licensed in the tenant. This can look like a product defect and is actually an entitlement setting.

4. The built-in ceiling: what you cannot tune

If triage does not resolve it, the next question is not "how do we fix this" but "is this fixable here." Built-in knowledge sources deliberately hide the retrieval machinery. These are the dials you do not get.

DialBuilt-in knowledge sourcesWhy it matters
Chunk size and overlapFixedDetermines whether a complete idea survives in one retrievable passage
Structure-aware chunkingNot configurableLong, hierarchical documents lose their section context when split naively
Number of passages retrievedFixed and smallCaps how much evidence the model can reason over in one answer
Ranking strategyNot selectableKeyword ranking and vector ranking fail on different questions; you cannot choose or blend
Metadata filters and scopingVery limitedNo reliable way to restrict answers by document type, region, product, or effective date
Text extraction from imagesBest effort, varies by pathScanned and image-heavy content may be partly or entirely invisible
Refresh timingScheduled, not on demandContent changes are not reflected immediately, and cannot be forced
Relevance measurementNot exposedYou cannot prove an improvement, only sense one

None of this is a defect. It is the cost of a knowledge source you can configure in ten minutes. The mistake is expecting an unconfigurable retrieval pipeline to perform like a tuned one on a corpus that needs tuning.

5. Seven signals you have outgrown built-in knowledge

Any one of these is a reasonable trigger for the conversation. Two or more, and the answer is usually already yes.

Signal 1

Scale of the corpus

You are approaching a platform cap on the number of knowledge objects or sources, or the body of content is growing steadily rather than being a fixed set.

Signal 2

Answers need breadth

Correct answers require evidence assembled from several documents at once, rather than from the single best-matching document.

Signal 3

Documents are long and structured

Policies, manuals, standards, and contracts, where a clause only means the right thing in the context of its section. Chunking strategy changes answer quality materially.

Signal 4

You need filtering, not just searching

Answers must be scoped by attributes such as document type, business unit, jurisdiction, product line, version, or effective date.

Signal 5

The content is not clean text

Scans, images, complex tables, and layout-dependent documents where you need explicit control over extraction rather than best-effort handling.

Signal 6

Content spans many systems

Knowledge lives across several repositories and you want it searched as one corpus, with consistent behavior, rather than as a set of separately configured sources.

Signal 7

You need to prove quality

Someone is accountable for accuracy and needs measurable retrieval quality, regression testing, and the ability to demonstrate that a change made things better.

Not a signal

One bad demo

A handful of poor answers is a triage task, not an architecture decision. Re-platforming to fix problems that were configuration issues simply relocates them.

6. What a purpose-built index gives you

Azure AI Search is the retrieval layer you build when the defaults are no longer sufficient. The point is not that it is more powerful in the abstract. The point is that every hidden decision from section 4 becomes an explicit one you own.

CapabilityWhat it changes
Configurable chunkingChoose chunk size and overlap, or chunk along document structure so headings and sections stay with the text they govern
Integrated vectorizationEmbeddings generated as part of the indexing pipeline, applied consistently to content and to queries
Hybrid retrievalKeyword and vector search run together, so exact terminology and paraphrased intent both find their target
Semantic rankingA reranking pass over candidates that materially improves which passages reach the model
Filters and facetsScope and filter on any metadata you index, which is what makes "only current policies for this region" possible
Document processing skillsLayout-aware extraction and optical character recognition for scanned and image-based content
Many sources, one indexIndexers across multiple repositories producing a single searchable corpus with consistent behavior
Measurable relevanceYou can evaluate retrieval quality, tune it, and show the difference

7. How it connects, and what you take on

In Copilot Studio, an Azure AI Search index is reached through Azure OpenAI On Your Data, configured on a generative answers node under the Classic data option. Two consequences are worth deciding on deliberately rather than discovering later.

Plan for this

Preview status

The Azure OpenAI connection for generative answers is preview functionality. Confirm current status before committing a production timeline to it, and design so the knowledge layer can be re-pointed if the integration path changes.

Plan for this

Orchestration constraint

Classic data sources are not available to generative orchestration. They live inside a topic-level generative answers node. If the agent relies on generative orchestration today, this is a design decision, not a detail.

You are also taking ownership of things the built-in sources handled for you:

  • The pipeline. Indexers, schedules, failure handling, and re-indexing when the content or the schema changes.
  • Freshness. Index currency becomes your responsibility and your service level, not a platform default.
  • Security trimming. Permission behavior must be designed into the index rather than inherited from the source system. Decide early whether the index carries access control or whether the corpus is uniformly accessible to the agent's audience.
  • Cost. A search tier, embedding and chat model deployments, document processing where needed, and the operational time to run it.
  • Evaluation. The upside of measurable relevance is that someone now has to measure it.
Realistic effort. A working, tuned index is typically a matter of weeks rather than days, and most of that time goes into content preparation and relevance tuning rather than into standing up the service. Budget for iteration, because the first index is rarely the one you keep.

8. The middle path

The choice is not binary. Several moves sit between "accept the defaults" and "build a custom retrieval stack," and they are usually worth exhausting first.

  • Switch ingestion path. Where a platform offers more than one way to connect the same repository, moving from a keyword-search-backed path to a vector-indexed one can change answer quality substantially with no architectural work.
  • Resolve licensing-dependent ceilings. Some size limits and search quality improvements are unlocked by entitlements already available in the tenant.
  • Split one agent into several. Narrower agents over coherent bodies of content retrieve better than one agent over everything, and they are easier to evaluate.
  • Use connected agents. Route a question to the agent that owns that domain, instead of asking one retriever to rank across unrelated corpora.
  • Fix the content. Deduplicate, retire superseded documents, and add the structure and metadata that retrieval can use. Cleaning a corpus often outperforms upgrading the retriever, and it is work you will need to do anyway.

9. Decision summary

SituationDo this
Some content answers, some never does Eligibility problem. Check size, protection, file type, and indexing state before anything else
Answers vary between users Permissions and authentication scopes, not retrieval
Same question answers inconsistently over time Citation and moderation behavior. Instrument with telemetry and tune instructions
Answers are shallow but the corpus is small and clean Change ingestion path, narrow the agent's scope, improve the content
Answers need evidence from many documents at once Move to a purpose-built index. This is a retrieval-depth limit you cannot configure around
You need scoping, filtering, or versioned answers Move to a purpose-built index with the metadata modeled deliberately
Someone is accountable for accuracy Move to a stack where retrieval quality can be measured and regression tested
A useful rule of thumb: built-in knowledge sources are the right answer when the corpus is bounded, reasonably clean, and the questions are about what a document says. A purpose-built index becomes the right answer when the corpus is open-ended, uneven, or the questions are about what the body of content collectively says.
