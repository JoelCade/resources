Connecting Copilot Studio to UKG

A field guide to authenticating a Copilot Studio agent against UKG Pro Workforce Management and UKG Pro HCM. Covers the certified connector landscape and its gaps, the two different authentication models, the malformed-request errors that look like credential failures but are not, and how to hand a token from an agent flow back to the agent. · August 2026

The one thing to remember: there is no Microsoft-certified authentication connector for UKG. You perform the token call yourself as an HTTP action, and the overwhelming majority of first-attempt failures are request-shape problems, not credential problems. UKG Pro Workforce Management wants a URL-encoded form body, and UKG Pro HCM wants Basic authentication plus a customer API key header. Get those two facts right and most of the pain disappears.

First, know which UKG you are talking to

UKG is two product families under one brand, and they do not share an authentication model. Teams routinely lose a day because they applied the workforce-management pattern to a human-capital-management endpoint. Establish this before you write a single action.

The certified connector landscape, and the gap in it

UKG publishes several certified connectors for Power Platform. They are genuinely useful for the data calls. What none of them do is hand you an authentication step, which is exactly the piece most teams assume will be there.

Available

Certified data connectors

  • UKG Pro WFM Employee — employee-scoped actions including accrual balance retrieval
  • UKG Pro WFM Timekeeping
  • UKG Pro WFM People
  • UKG Pro HCM

Published by UKG, classified Premium, and at the time of writing carrying Preview status. Connection is configured with the Pro WFM vanity URL as a secure string.

Not available

A certified authentication connector

There is no first-party or UKG-published connector whose job is to obtain the token. You have two supported ways to close that gap:

  • A raw HTTP action in a cloud flow or agent flow, which is the fastest path and the one worth starting with
  • A custom connector you build and own, which is better once several flows need the same call
Plan for the constraints early. The certified UKG connectors throttle at roughly 100 calls per connection per 60 seconds, and they are not offered in the US Government, Department of Defense, or China sovereign clouds. If your agent serves a large deskless population or a regulated environment, confirm both of these before you design the interaction pattern.

Path A — the UKG Pro WFM token call

The token endpoint follows this shape, where the host is your tenant vanity URL:

POST https://{tenant}.{region}.mykronos.com/api/authentication/access_token

The body must be a URL-encoded form, not JSON

This is the single most common mistake. The header says application/x-www-form-urlencoded because that is what the endpoint requires, but people paste a JSON object into the body because that is what every other modern API accepts. UKG does not. Send a flat query string on one line, with no braces, no quotation marks, and no trailing ampersand.

Content-Type: application/x-www-form-urlencoded

grant_type=password&username=SERVICE_ACCOUNT&password=ENCODED_SECRET&client_id=CLIENT_ID&client_secret=CLIENT_SECRET&auth_chain=OAuthLdapService
FieldNotes
grant_typeUnderscore, not a hyphen. OAuth uses grant_type, and grant-type is silently unrecognized.
username / passwordA UKG service account, provisioned by a UKG administrator. Never a named human user.
client_id / client_secretIssued with the API registration on the UKG side.
auth_chainOAuthLdapService for tenants federated to LDAP, otherwise OAuthService. Getting this wrong produces an authentication failure that looks like a bad password.
appkey headerSome tenants additionally require an application key sent as a header. Confirm with your UKG administrator rather than assuming.

Percent-encode every special character

In a form body, characters that are meaningful in a URL are interpreted as such. A hash character in a password is the worst offender, because everything after it is discarded as a URL fragment and you end up sending a truncated secret with no error to tell you so.

CharacterEncode asWhy it matters
#%23Starts a fragment. Silently truncates everything after it.
&%26Starts a new field. Splits your value into two garbage fields.
=%3DSeparates key from value. Corrupts field parsing.
+%2BDecoded as a space on the receiving end.
@%40Reserved. Encode it for safety.
space%20Invalid raw in a query string.

Reading the error that looks like a platform bug

Symptom: connectorRequestFailure with HTTP 500, and an inner message of Error parsing undefined value. Path '', line 1, position 1.

That message is not describing a broken connector and it is not a Power Platform defect. It means UKG returned an empty or non-JSON response body, so the parser had nothing to work with. The request was rejected as malformed before UKG ever evaluated the credential. Work the causes in this order:

1

Body format mismatch

A JSON body sent against a form-urlencoded content type. By far the most likely cause. Rewrite the body as a flat query string.

2

Hyphenated grant type

grant-type instead of grant_type. Common when the body was transcribed from a hand-written example.

3

Unencoded special character

Usually a hash in the password. Encode the value and retry before you go asking for a credential reset.

4

Missing tenant-specific requirements

An absent appkey header or the wrong auth_chain value for a federated tenant.

Only after all four are ruled out is it worth escalating to UKG. Raising a credential ticket first is the standard way these engagements lose a week.

Path B — the UKG Pro HCM call

HCM uses a different model entirely. There is no token exchange. Each request carries HTTP Basic authentication built from a UKG service-account credential, alongside a customer API key header.

ElementValue
AuthenticationHTTP Basic, using a UKG service account created by a UKG administrator
Required headerUS-Customer-Api-Key
Content negotiationAccept: application/json
Typical first endpointEmployment Details, retrieving an employee record by company plus employee identifier
Useful behaviorThe endpoint supports pagination and date filters, so you can bound the response rather than pulling everything
Two practical traps. First, let your API client generate the Basic authorization header rather than hand-assembling the base64 string, which is a frequent source of an HTTP 401 or 415 that is really a formatting error. Second, confirm which identifier the endpoint expects. Organizations often have a company employee number, a payroll identifier, and a directory identifier in circulation, and only one of them will resolve.

Prove the call in an API client such as Postman before you build it in Power Automate. Debugging authentication and flow expression syntax at the same time is a false economy.

Getting the result back to the agent

This is where a working flow still fails to help the agent. A conventional cloud flow does not surface its internal values to a Copilot Studio agent. The authentication and data logic has to live in an agent flow, and the values you want the agent to see must be declared as outputs on the Respond to Agent action.

User Asks the agent about a balance, schedule, or employment detail
→
Copilot Studio agent Orchestration selects the UKG tool and passes the employee context
→
Agent flow HTTP token call, then Parse JSON, then the certified UKG data action
→
Respond to Agent Returns typed outputs the agent can phrase back conversationally

Parse the token response defensively

The response comes back as JSON even though the request was form-encoded. Mark only access_token as required, because some tenants omit the optional members and a stricter schema will fail validation on a response that was actually fine.

{
  "type": "object",
  "properties": {
    "access_token":  { "type": "string" },
    "token_type":    { "type": "string" },
    "expires_in":    { "type": "integer" },
    "refresh_token": { "type": "string" },
    "scope":         { "type": "string" },
    "id_token":      { "type": "string" }
  },
  "required": ["access_token"]
}

Generate the schema for the data response from a real payload rather than writing it by hand. Reference the token downstream from the Parse JSON output, and pass it as a bearer value on the subsequent call.

Hardening it for production

Never inline the secrets

Hold the service-account credential, client secret, and API key in Azure Key Vault, surfaced through Dataverse environment variables. This keeps them out of the flow definition, out of solution exports, and out of the hands of anyone with maker access to the environment.

Do not fetch a token per turn

Tokens carry an expiry. Calling the token endpoint on every conversational turn burns throttle budget against a 100-call-per-minute ceiling and adds latency the user feels. Reuse a token for its lifetime and refresh on expiry or on an authentication failure.

Handle the empty answer

Decide what the agent says when the employee is not found, when the identifier is ambiguous, or when UKG is unavailable. Without an explicit path, generative orchestration will improvise, and improvising about someone's leave balance is the worst possible failure mode.

Check your data loss prevention policy

The UKG connectors are Premium and third-party. Confirm they sit in a policy group that permits combination with the other connectors your agent uses, and do this before the build rather than at deployment.

A sensible build order

1

Get the credentials provisioned

Service account, client identifier and secret, API key, and confirmation of whether an application key header and which authentication chain your tenant needs. This has a lead time. Start it first.

2

Prove the call outside Power Platform

Succeed in an API client. You are isolating authentication from flow authoring, and it is much faster to iterate.

3

Rebuild it as an HTTP action in an agent flow

Move the secrets into environment variables backed by Key Vault as you go, rather than promising to do it later.

4

Chain the certified data action

Add the UKG connector action, supplying the vanity URL on the connection and the token from the preceding step.

5

Expose typed outputs and register the flow as a tool

Declare the fields on Respond to Agent, then add the flow to the agent as a tool with a description clear enough that orchestration routes to it for the right questions and leaves it alone for the wrong ones.

A note on sequencing the wider solution. Most organizations reach this integration in a second phase. Phase one is a knowledge-grounded agent answering policy and procedural questions from documents, which needs no UKG connectivity at all and delivers value quickly. Transactional lookups against UKG are phase two, and they are where authentication, identity resolution, and error handling all become real. Do not let the ambition of phase two delay the shipping of phase one.
